# Windows: ручная проверка персонажа, памяти и ИИ

Ручную приёмку выполняет владелец продукта. Автоматические результаты и закрытые задачи не подтверждают Windows-прогон: фиксировать версию, окружение и результат каждого сценария.

## Запуск и доступные режимы

Подготовить окружение по [корневому README](../../README.md#подготовка). Все команды ниже выполняются из корня репозитория.

```powershell
node scripts/wisp.mjs dev
```

Совместный launcher запускает встроенный backend и desktop с единым API v1. Chat включает память, карточку и appraisal; touch, summary и observation используют тот же префикс. Сетевые инициативы выключены по умолчанию. Фактические возможности и ограничения — в [backend README](../../backend/docs/README.md#поддерживаемые-сценарии).

Для локального Mock использовать `node scripts/wisp.mjs dev:frontend` без `WISP_BACKEND_URL`. Для отдельного backend и сетевых инициатив:

```powershell
$env:WISP_BACKEND_URL = "http://127.0.0.1:8000"
$env:WISP_AI_EVENTS_ENABLED = "true"
node scripts/wisp.mjs dev:frontend
```

Выбора версии API нет. `WISP_AI_EVENTS_ENABLED=false` отключает инициативы, сохраняя память в диалоге. Изменение конфигурации требует перезапуска Main. LLM-ключ задаётся только серверу. Удалённый endpoint требует HTTPS base URL без endpoint path/query/credentials и подтверждённых оператором условий доступа и обработки данных. Development loopback не является конфигурацией packaged-клиента.

Сценарии 2–5 проверяют память и сетевые ответы; сценарий 6 требует включённых events. Недоступный сценарий отмечать NOT RUN с причиной.

Проверить dev и отдельно уже предоставленный portable: записать commit, Windows/Electron версии, userData, размер артефакта и версии desktop/backend. Подготовка portable — отдельный packaging scope; `npm run build` запрещён инженерными правилами.

## Сценарии

1. **Локальная жизнь.** Запуск, окно, меню, drag, облачко, игра: поймала/промахнулась/потеряла цель/прервана. После игры возвращается к обычным занятиям. Повторить при остановленном backend: ввод и движение продолжаются.
2. **Факт и restart.** Отправить `Меня зовут Аня`, дождаться завершённого ответа. Закрыть приложение штатно и запустить снова; спросить имя. Затем `Меня зовут Лена` и сразу вопрос об имени: актуальным должно быть новое значение. Старая реплика не должна побеждать исправленный структурированный факт.
3. **Границы памяти.** Временная роль, цитата чужого утверждения и выдуманный моделью факт не переписывают профиль. MVP распознаёт конечный набор явных формулировок из [Memory §9](engine/MEMORY_ENGINE.md#9-p15-a02-явные-знания-и-простой-recall); произвольная фраза не обязательно становится структурированным фактом.
4. **Игра после restart.** Завершить реальную игру, перезапустить и спросить про игру с курсором. Ответ должен учитывать сохранённый допустимый исход, не обещать несостоявшееся участие пользователя и не подменять физическое событие.
5. **Постепенная адаптация.** Одно `Мне нравится игра с курсором` не меняет резко характер. Разнесённые во времени подтверждённые предпочтения накапливаются с пятиминутным gate; после restart сохраняются. Положительный/отрицательный опыт слегка меняет вероятность самостоятельной допустимой игры, не гарантирует конкретный случайный исход и не отменяет quiet/sleep/другие ограничения.
6. **AI-инициатива и ответ.** Сетевые события возможны только спустя пять минут после старта, при включённом флаге и пройденных локальных gates. Максимум два event-запроса в час, между ними минимум пять минут. После показанной AI-фразы ответить `почему?`: ближайший принятый вопрос в пределах 60 секунд получает эту фразу как контекст. Старые инициативы после restart повторно не отправляются.
7. **Ненавязчивость и сеть.** Quiet, меню, сон и приоритетный ввод не допускают фоновой AI-речи. Новое сообщение пользователя отменяет фоновый запрос. Остановка backend, timeout/quota и поздний ответ не возобновляют старую игру, не возвращают удалённую память и не мешают локальным действиям.
8. **Пределы.** Записать CPU/RAM, задержку ответа и фактический расход тестовой сессии. Клиентские лимиты: шесть обращений/минуту и сто/сессию, включая события. Сброс диалога/reload не обнуляет сетевой бюджет. Исчерпание объясняется отдельным уведомлением без удаления последнего ответа персонажа.

## Состояние и очистка памяти

В MVP нет отдельного нового Settings UI для памяти. При доступных Renderer DevTools состояние можно прочитать через `await window.wispAPI.getMemoryStatus()`: ожидается `persistent`; `volatile` означает, что текущий запуск не подтверждает постоянное хранение. Не начинать взаимодействие до окончания startup restore, если проверяется именно восстановление прежнего состояния: ранний пользовательский ввод отменяет запоздалое восстановление.

Полный transactional reset реализован в typed `window.wispAPI.clearMemory` и проверен автоматическими сценариями, но отдельной пользовательской кнопки в этих задачах не добавляли. Контракт команды/receipt — [IPC DTO](../src/shared/ipc-contracts.ts), пример проверки — [memory restart test](../tests/application/memory-restart.test.ts). Обычный сброс диалога не означает удаления facts/игровых эпизодов. Полная локальная очистка также не обещает немедленного удаления уже переданных данных на сервере/у провайдера.

Для каждого дефекта записать commit/окружение, шаги, ожидаемое/фактическое поведение и приложить безопасный фрагмент лога без секретов. Не отмечать непроверенные сценарии как пройденные.
