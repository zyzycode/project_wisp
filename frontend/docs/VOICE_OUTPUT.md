# Локальная озвучка ответов

При обычном запуске Wisp озвучка включается автоматически после готовности диалога
и локальной модели. Кнопка под персонажем выключает/включает голос для **следующих**
успешных ответов диалога. Голос — Ono_Anna, текущая locale приложения — русский.
При выключенной озвучке ответ появляется текстовым пузырём. При включённой —
звучит голосом вместо пузыря; во время подготовки отображается статус.
Если синтез или воспроизведение не удались, тот же актуальный ответ появляется
текстом. Текст ответа сохраняется в истории диалога при любом способе вывода.
«Остановить речь» отменяет текущую подготовку или воспроизведение. Ошибки,
локальные подтверждения, игровые реплики и инициативы пока выводятся текстом.
Переключение действует на следующие ответы; выключение отменяет текущий голос,
остановленная или устаревшая реплика повторно не показывается и не произносится.

Во время подготовки и воспроизведения микрофон на паузе, аудио не накапливается.
После нормального окончания слушание продолжается, если режим микрофона остался
включён. Принудительная отмена, quiet, reset/reload или потерянное подтверждение
воспроизведения отзывают микрофон; включите его снова явно. Звук после reset/reload
тоже включается явно. Истечение срока текстового пузыря не прерывает голос.
Startup-включение одноразовое: выключенный пользователем или отозванный режим не
включается снова при обновлении состояния, remount или unlock/resume. Новый обычный
запуск приложения снова использует включённый default; ошибки не запускают retry.

В основном меню Wisp раздел звука содержит переключатели микрофона и озвучки,
выбор устройства вывода и кнопку проверки коротким тоном. Выбранное устройство
сохраняется на этом компьютере. «Системное устройство» использует системный выход;
конкретные наушники/колонки выбираются отдельно. Wisp не меняет общий выход системы.
Названия устройств могут появиться после разрешения доступа к микрофону.
При выключенном микрофоне список может быть ограничен: сохранённый выбор остаётся,
его доступность проверяется перед воспроизведением, без включения микрофона.
Доступ к выбранному выходу разрешён только на время текущего воспроизведения или
проверки; он не даёт разрешения на запись микрофона или камеры.
Если выбранное устройство отключено или доступ запрещён, Wisp показывает ошибку
и актуальный ответ текстом; незаметного переключения на другие колонки нет.
Повторное подключение не проигрывает старый ответ. Проверка звука не запускает TTS
и использует тот же выбранный выход с приостановкой голосового ввода.

## Исполнение и поставка

[Qwen3-TTS 0.6B CustomVoice](https://github.com/QwenLM/Qwen3-TTS), speaker `ono_anna`,
[CPU-int4 ONNX export](https://huggingface.co/onnx-community/Qwen3-TTS-12Hz-0.6B-CustomVoice),
код/веса заявлены авторами под Apache-2.0. Inference адаптирован из
[эталонного multigraph inference](https://huggingface.co/onnx-community/Qwen3-TTS-12Hz-0.6B-CustomVoice/blob/18b0bf898d211718bc33082fadc36a448e0cbc0c/inference.py).
Полные revisions, размеры и SHA256 находятся в
[manifest](../src/infrastructure/voice-output/model-manifest.ts).
Шесть graphs и четыре tokenizer/config файла занимают 1 070 552 426 байт.

`node frontend/scripts/prepare-tts-model.mjs` проверяет cache и при необходимости
скачивает закреплённые файлы только на машине разработчика/сборки. Vite вызывает
подготовку автоматически; `extraResources` доставляет эти же файлы в приложение.
Установленный Wisp работает offline, без Python, облачного TTS и runtime-download.
Как у голосового ввода, доступность native ORT зависит от поддерживаемых prebuilt
платформ; Windows/macOS требуют отдельного native smoke.

Main проверяет файлы и авторизует только identity текущего успешного ответа;
Renderer не передаёт произвольный текст. ONNX исполняется в отдельном Main-owned
Electron utility process, изолирующем native crash от процесса приложения,
с числом intra-op CPU потоков `min(8, availableParallelism())`, inter-op=1 и
выключенным spinning у session pools. Ограничения — 120 s, 1500 frames и 120 s PCM. Нет очереди,
повторного озвучивания отменённого ответа, WAV-файлов и логирования текста/аудио.
Токенизатор сверяется с official Python Qwen2Tokenizer 4.57.3 на RU/EN, числах,
пунктуации, newline, emoji и Unicode NFC. Новых runtime-зависимостей нет.
Cancel/timeout/dispose прекращают дочерний процесс; новый запускается только после
подтверждённого exit. Ограничения retirement и состав приватного IPC заданы в UI Spec.

## Проверка и ограничения

Адресные тесты: `node scripts/wisp.mjs test:frontend tests/voice-output tests/voice`.
После подготовки ресурсов отдельный реальный offline probe:
`WISP_TTS_PROBE=1 node scripts/wisp.mjs test:frontend tests/voice-output/model-probe.test.ts`.
Обычные unit gates не загружают и не исполняют настоящую TTS-модель.

Сквозная проверка настоящей модели в Electron вплоть до Web Audio playback и ack:
`WISP_TTS_NATIVE_PROBE=1 node scripts/wisp.mjs smoke:desktop /tmp/wisp-tts-native`.
Используются отдельный профиль, фиксированная синтетическая реплика и реальный TTS;
физический микрофон и provider calls не нужны. Проверяется ненулевой PCM.
В том же launcher значения `cancel-load`, `cancel-run` и `crash` вместо `1`
проверяют отмену с последующим новым синтезом, warm dispose и изоляцию аварии child.

В предварительном standalone Linux CPU probe прежний скомпилированный Node worker
сгенерировал 159360 samples
(6.64 s PCM) за 47.91 s с холодного старта, peak RSS всего процесса 1600300 KiB,
CPU time ~99.44 s. Main heartbeat продолжал работать. Это измерение одного
прогона, не замер памяти текущего utility process и не подтверждение качества на слух.
Полный ответ синтезируется до начала playback: задержка может быть большой;
длинный ответ при deadline останется только текстовым. Потоковая озвучка не включена; CPU tuning текущего utility process описан ниже.

Канонические границы: [UI Spec](engine/UI_SPEC.md#локальный-голосовой-вывод).


## Воспроизводимые замеры CPU

Из корня после обычной подготовки pinned ресурсов:

```sh
node frontend/scripts/benchmark-tts.mjs 2 1 full
node frontend/scripts/benchmark-tts.mjs 8 0 full
```

`short` вместо `full` проверяет только приветствие; full добавляет вопрос и фразу
из двух предложений. Каждая фраза повторяется дважды с seed=42 в отдельном
процессе пробы; production sampling не меняется. Проба проверяет SHA256, не
скачивает модель и не пишет PCM. Вывод: verification/load, synthesis/PCM duration,
RTF, graph times/calls, CPU time, peak RSS и heartbeat тестового Node parent.
Предел каждого этапа — 120 s, затем завершается только дочерний процесс пробы;
незавершённый синтез не считается успешным и не получает выдуманный RTF.
Это process-cold запуск с обычным файловым кешем ОС, не cold disk.

Для настоящего utility process → выбранный аудиовыход → Web Audio start/end/ack:

```sh
WISP_TTS_NATIVE_PROBE=1 node scripts/wisp.mjs smoke:desktop /tmp/wisp-tts-latency
```

Native smoke использует отдельный профиль, synthetic microphone и фиксированный
ответ, seed только в test-owned utility entry, без AI provider calls. `voiceLatency`
отделяет mock-provider time, ожидание Dialogue, synthesis, PCM duration и первый
`AudioBufferSourceNode.start()`, показывает Main heartbeat и память utility process.
Вызов `start()` — программный onset, не акустический замер звука колонок.
Числа реального AI-провайдера этим smoke не подтверждаются.

На проверенном Ryzen 7 5800X/Linux увеличение CPU cap ускоряет короткий синтез
примерно вдвое, но RTF остаётся выше 1; быстрого разговорного отклика это пока не
обеспечивает. Результат других CPU требует собственной пробы. Streaming не включён:
при RTF>1 ранний старт сам по себе не обеспечивает речь без пауз. Измерения и
сравнение runtime/русских альтернатив публикуются в [#149](https://github.com/zyzycode/project_wisp/issues/149).
