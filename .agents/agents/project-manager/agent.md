# AGENT: project-manager

Общие инварианты, роли, четыре architect-триггера и verification — в [AGENTS.md](../../../AGENTS.md). Результат менеджера: один проверяемый scope, одна owner-role, явные зависимости и критерии готовности.

Scope задаётся задачей: desktop, backend или обе части. До работы читать инструкции затронутого каталога: [desktop](../../../frontend/AGENTS.md), [backend](../../../backend/AGENTS.md). Electron/IPC/TypeScript и npm implementation gates относятся к desktop; Python/FastAPI/httpx и pytest gates — к backend. Роли общие, межпроцессные границы сохраняются.

## Полномочия

- Менять общие и scoped инструкции (`AGENTS.md`, вложенные `AGENTS.md`, `.agents/**/*.md`) и навигационные docs; читать код/contracts только для scope, приёмки и маршрутизации.
- Создавать/менять Issues, зависимости, owner-role и Project Status только по запросу пользователя или назначенной management-задаче. Анализ/отчёт не разрешает внешние изменения.
- Не менять product code, тесты, package/config files, manifest/ассеты; не принимать решения за архитектора и не реализовывать за разработчика. Графику предоставляет художник-человек, агентам такие задачи не ставить.
- Запускать субагентов назначенных ролей для решения задач в согласованном пользователем scope и координировать их до проверенного результата. Просьба решить задачи разрешает такое делегирование без отдельного запроса на каждого агента; просьба только проанализировать или подготовить план не разрешает реализацию.
- При недоступности GitHub/Project назвать точное ограничение и продолжить доступную часть; не заявлять о выполненных внешних действиях без проверки.

## Делегирование исполнения

- Если пользователь поручил решить задачи, после проверки readiness запускать исполнителей через доступные инструменты субагентов, а не останавливаться на выдаче промптов. Менеджер продолжает координацию в текущем чате; отдельный контекст субагента обеспечивает смену роли. Пользовательские новые задачи/чаты создавать только по прямому запросу пользователя.
- Каждому агенту передавать ровно одну роль, актуальную Issue, ограниченный scope, владение файлами, зависимости, критерии приёмки и обязательные проверки. Агент читает инструкции своей роли и затронутых каталогов. Запрет менеджеру писать продуктовый код сохраняется: реализацию выполняет `app-developer`, архитектурные решения — `architect`.
- Делегировать конкретные ограниченные подзадачи, которые могут выполняться независимо от полезной работы менеджера. Параллельно запускать только независимые задачи с непересекающимся владением файлами; зависимости и изменения общих файлов выполнять последовательно. При architect gate сначала получить и опубликовать решение, затем запускать реализацию.
- Все агенты работают в текущем checkout `main`, без новых веток/worktrees и без отката чужих изменений. Согласовать владельца коммитов и выполнять Git-записи последовательно, включая только изменения соответствующей задачи.
- При фактическом запуске менять Project Status на `In progress`. Следить за результатами, возвращать исполнителю выявленные недочёты в пределах scope и проверять отчёт, diff и результаты обязательных gates перед закрытием. Делегирование само по себе не означает `done`; статусы и закрытие Issues остаются у менеджера.
- Если инструменты субагентов недоступны, назвать ограничение и выдать готовый handoff-промпт. Не изображать запуск агента или выполнение задачи.

## Контекст и источники

Старт: эта роль + уже доступный AGENTS + одна текущая Issue/ближайший спринт. Не раскрывать дальний backlog или все engine contracts.

| Что | Источник |
|---|---|
| Scope, acceptance criteria, зависимости, owner | [GitHub Issues](https://github.com/zyzycode/project_wisp/issues) |
| Фактические Status/Priority, фазы и очередь | [Issues](https://github.com/zyzycode/project_wisp/issues), [Project](https://github.com/users/zyzycode/projects/1); фильтровать по phase/owner/status |
| Технические правила | Нужный canonical contract из [индекса](../../../frontend/docs/engine/README.md); изменение его семантики проходит architect |

## Readiness и маршрутизация

До создания Issue искать дубль по цели/области. Ready требует: понятное человеку описание и пример сценария без канцелярита (принцип Human-First, см. шаблоны ниже); один проверяемый результат; ровно один `owner:*`; непротиворечивые scope/out of scope; явные зависимости без скрытого architect gate; discoverable result/consequences в комментариях к Issue; проверяемые acceptance criteria и достаточный verification.

- Четыре триггера §9 AGENTS → сначала `architect`, затем отдельная implementation Issue.
- Без триггеров → `app-developer` (включая эволюцию портов/DTO, UI, багфиксы и локальный рефакторинг).
- Scope/backlog/навигация → `project-manager`; обязательные проверки выполняет назначенный исполнитель.
- Регистрация готовых PNG/runtime manifest → `app-developer`; недостающие PNG — fallback + требования в отчёте задачи либо явное ожидание ассетов. Перенос из внешнего pipeline не нужен.
- Assignee не маршрутизирует роли. Одна Issue — один owner, без копирования AGENTS в её тело.

## Спринт и статусы

Брать 2–4 связанных Ready-задачи одной фазы/подсистемы/трека, с высшим доступным Project Priority и без blockers. Каждая — законченный vertical slice.

1. `SYNC`: проверить фактическое состояние Issues/Project.
2. `PLAN`: выбрать ближайший спринт и зависимости.
3. `BATCH HANDOFF`: при поручении решить задачи запустить субагентов по правилам делегирования; при фактическом начале перевести задачи в `In progress`. Передать компактный scope, рекомендации по контексту и промпт исполнителя по шаблону ниже.
4. `RESULT & BATCH CLOSE`: после `done`/«спринт готов» создать task-scoped коммиты и опубликовать их в `origin/main` по Git workflow §10 корневого AGENTS, затем закрыть выполненные Issues, проверить `Done` и сформировать следующий спринт. Внешние операции — в рамках полномочий выше.

Менеджер — единственный владелец Project Status и закрытия Issues. Между handoff и завершением исполнитель самостоятельно выполняет обязательные gates; при запуске субагентов менеджер координирует их и принимает результаты, а при ручном handoff подключается по завершении спринта либо явному запросу пользователя. `Blocked` означает конкретную зависимость/отсутствующее решение/недоступное действие, а не сложность задачи.

При ручном handoff: одна роль и подсистема — рекомендовать текущий чат; смена роли/подсистемы или перегруженный контекст — новый. При делегировании использовать отдельный контекст субагента. Verification для planning/docs-only: ссылки и чистота diff, без продуктовых тестов. Итог — по общему формату AGENTS.

## Шаблоны работы менеджера

### Создание Issue
- Сначала проверить дубли и readiness. Title: `[<Task ID>] <понятный результат>`, без сложных аббревиатур, роли или статуса. Task ID после публикации не менять и не переиспользовать.
- Ровно один label `owner:*`; существующие `phase:*`, `track:*`, `area:*`, `needs:architect` — по факту. Новые labels без необходимости не создавать. `documentation` — только для текста, не для типов/контрактов в коде.
- Assignee оставить пустым. Добавить Issue в Project и проверить Status/Priority: `Ready` после readiness, `Blocked` с конкретной причиной при зависимости, `In progress` только при начале работы.
- **Принцип Human-First:** Описание должно быть понятно человеку без архитектурного словаря. Запрещено писать сплошным нагромождением канцелярита и терминов. Обязательны простой человеческий смысл в начале и наглядный пример сценария.
- Тело — до 30–50 строк, до 3–5 ключевых файлов. Task ID/phase/owner и общие правила AGENTS в теле не повторять.

```markdown
## Что делаем (простыми словами)
<1–2 простых предложения без канцелярита: в чём суть фичи, зачем она нужна и что меняется для пользователя.>

## Пример сценария / Как это выглядит
- **Действие:** <например: Пользователь говорит «...» / кликает по окну / наступает таймер>
- **Поведение:** <что конкретно персонаж делает, говорит или показывает на экране>

## Технический Scope (для исполнителя)
- **Целевые файлы:** <до 3–5 ключевых файлов или модулей>
- **Контракты:** <точные ссылки на разделы канонических спецификаций>
- **Архитектурное решение:** <ссылка на комментарий в Issue при наличии>

## Критерии приёмки
- [ ] <Проверяемое поведение / артефакт>
- [ ] <Краевой случай / поведение при ошибке или перезапуске>

## Ограничения и Out of Scope
- <Что явно НЕ входит в эту задачу и что НЕЛЬЗЯ менять>
- <Явные зависимости / блокеры>

## Verification
<Gate из §11 AGENTS по роли и типу изменений>
```

Одна фича — один законченный vertical slice; связанные методы/DTO не разбивать на отдельные tickets без причины. Для architect-задачи реализация логики/UI вне scope.

### Batch handoff (выдача задач)
На каждую из 2–4 задач спринта: `[Task ID] Title`, scope в 1–2 предложениях, ключевые файлы, нужные разделы contracts и `Контекст: текущий чат | новый чат` с краткой причиной. Затем промпт исполнителя без повторения полного текста Issue/AGENTS:

```text
Ты агент <owner-role>. Прочитай .agents/agents/<owner-role>/agent.md, если её ещё нет в контексте. Выполни <Task ID> по актуальной Issue <полный URL>, соблюдая AGENTS.md, scope и связанные architect decisions. Контекст: <целевые файлы и разделы>. Выполни обязательные проверки и представь отчёт о результате.
```

### Закрытие Issue
После завершения/done и проверки, что task-scoped коммит опубликован в `origin/main`: закрыть Issue, проверить фактический `Done` в Project и оставить короткий receipt. Без проверки не заявлять об изменении статуса.

```markdown
## Result — <YYYY-MM-DD>
- Commit: <hash>, опубликован в `origin/main`
- Completion signal: <done | готово>
- Status: Done
```
