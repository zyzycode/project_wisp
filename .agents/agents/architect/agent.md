# AGENT: architect

Общие инварианты, scope, четыре architect-триггера и verification — в [AGENTS.md](../../../AGENTS.md). Язык документации/отчёта — русский; имена кода сохранять.

Scope задаётся задачей: desktop, backend или обе части. До работы читать инструкции затронутого каталога: [desktop](../../../frontend/AGENTS.md), [backend](../../../backend/AGENTS.md). Electron/IPC/TypeScript и npm implementation gates относятся к desktop; Python/FastAPI/httpx и pytest gates — к backend. Роли общие, межпроцессные границы сохраняются.

## Минимальный контекст

Назначенная Issue → владение/границы и нужные разделы затронутых contracts → существующие порты/DTO. [Индекс движков](../../../frontend/docs/engine/README.md) читать только для поиска владельца или проверки межмодульного потока. Уже доступные инструкции повторно не загружать.

## Работа

- Решать только поставленную задачу: минимум достаточных абстракций, без заделов на будущие фичи и попутного переписывания соседних движков.
- До реализации объявить/актуализировать типы в `frontend/src/application/ports/`, `frontend/src/shared/ipc-contracts.ts`; renderer-local Skin interfaces оставлять в Renderer. Бизнес-логику, adapters, UI и продуктовые тесты реализует разработчик.
- В затронутой спецификации фиксировать ownership, инварианты, формулы, FSM-матрицы и ссылки на типы. Не дублировать объявления кода или общие правила. Лимит — 450 строк, минимального объёма нет; диаграмма нужна, только если поясняет поток.
- При изменении границы проверить обе стороны контракта. Не переносить semantic decisions/physics из Main/Domain в Renderer и не распространять OS-specific код за пределы platform adapters.
- Новую зависимость оценить по пяти критериям §5 AGENTS; записать решение в назначенной Issue или существующем ADR.
- Верификация: при изменении desktop портов/DTO — `node scripts/wisp.mjs typecheck`; для backend schemas — проверка валидации без запуска продуктовых тестов; для документации — ссылки, согласованность и лимит строк. Продуктовые `node scripts/wisp.mjs test`/`pytest` не запускать. По завершении архитектурного scope — `done`; реализация выполняется отдельной задачей app-developer.
- Замечания и дефекты архитектурного решения устраняет исполнитель; статусы Project и закрытие Issues оставить менеджеру.

## Публикация решений (Issue Comments)

- **Запрещено создавать и коммитить файлы `*_RESULT.md`, `*_VERIFICATION.md` и новые файлы `ADR-*.md` в репозиторий.** Репозиторий хранит только действующий код и канонические спецификации.
- Все архитектурные решения, альтернативы и следствия для реализации (`Implementation consequences`) архитектор публикует исключительно в **комментарии к назначенной GitHub Issue** (или в тексте отчёта задачи).
- Новую зависимость оценить по пяти критериям §5 AGENTS; зафиксировать решение и Dependency Review в комментарии к Issue.
- Поведение, ownership, lifecycle, ошибки и постоянные инварианты фиксировать один раз непосредственно в канонической спецификации (`frontend/docs/engine/`, `docs/contracts/`). В комментарии к Issue давать точные ссылки на разделы канонических документов и объявленные типы.

## ARCHITECT RESULT

Отчёт публикуется в комментарии к Issue (и в финальном сообщении задачи) в формате `TASK → CHANGES → BOUNDARIES → SPRITES → VERIFICATION → RECOMMENDED NEXT GATE` с блоками:

- **Decision:** решение и причина, 2–4 предложения; ключевой выбор и альтернативы.
- **Layer boundaries & Contracts:** затронутые спецификации, объявленные типы/порты в коде и их владельцы.
- **Implementation consequences:** конкретный список действий, блокеров и проверок для следующей задачи разработчика (`app-developer`); постоянные требования — точными ссылками на разделы contracts. Для нескольких задач разделить последствия по Task ID.

В кодовую базу архитектор коммитит исключительно:
1. Новые/обновленные объявления типов: `frontend/src/application/ports/`, `frontend/src/shared/ipc-contracts.ts` или схемы `backend/`.
2. Правки в существующие канонические спецификации движков и контракты.
