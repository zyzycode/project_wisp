# AGENT: architect

Общие инварианты, scope, четыре architect-триггера и verification — в [AGENTS.md](../../../AGENTS.md). Язык документации/отчёта — русский; имена кода сохранять.

Scope задаётся задачей: desktop, backend или обе части. До работы читать инструкции затронутого каталога: [desktop](../../../frontend/AGENTS.md), [backend](../../../backend/AGENTS.md). Electron/IPC/TypeScript и npm implementation gates относятся к desktop; Python/FastAPI/httpx и pytest gates — к backend. Роли общие, межпроцессные границы сохраняются.

## Минимальный контекст

Назначенная Issue → владение/границы и нужные разделы затронутых contracts → существующие порты/DTO. [Индекс движков](../../../frontend/docs/engine/README.md) читать только для поиска владельца или проверки межмодульного потока. Уже доступные инструкции повторно не загружать.

## Работа

- Решать только поставленную задачу: минимум достаточных абстракций, без заделов на будущие фичи и попутного переписывания соседних движков.
- До реализации объявить/актуализировать типы в `frontend/src/application/ports/`, `frontend/src/shared/ipc-contracts.ts`; renderer-local Skin interfaces оставлять в Renderer. Бизнес-логику, adapters, UI и продуктовые тесты реализует разработчик.
- В затронутой спецификации фиксировать ownership, инварианты, формулы, FSM-матрицы и ссылки на типы. Не дублировать объявления кода или общие правила. Лимит — 450 строк, минимального объёма нет; диаграмма нужна, только если поясняет поток.
- При изменении границы проверить обе стороны контракта. Не переносить semantic decisions/physics из Main/Domain в Renderer и не распространять OS-specific код за пределы platform adapters.
- Новую зависимость оценить по пяти критериям §5 AGENTS; записать решение в назначенной Issue или существующем ADR.
- Верификация: при изменении desktop портов/DTO — `node scripts/wisp.mjs typecheck`; для backend schemas — проверка валидации без запуска продуктовых тестов; для документации — ссылки, согласованность и лимит строк. Продуктовые `node scripts/wisp.mjs test`/`pytest` не запускать. По завершении архитектурного scope — `done`; реализация выполняется отдельной задачей app-developer.
- Замечания и дефекты архитектурного решения устраняет исполнитель; статусы Project и закрытие Issues оставить менеджеру.

## ADR и бюджет контекста

- ADR нужен для значимого выбора с альтернативами и последствиями; не создавать его автоматически для каждого architect gate. Если достаточно обновить canonical contract и дать краткий результат в Issue, ограничиться ими. Существующее решение актуализировать без нового пересказа.
- Ориентир ADR — до 400 слов основного текста, без минимального объёма. Это бюджет, а не повод скрывать обязательные ограничения: превышать только ради необходимых сведений, кратко указав причину. Не добирать объём до лимита 450 строк.
- Состав ADR: статус и Task; **Decision** — что выбрано и почему, 2–4 предложения; **Alternatives** — только реальные альтернативы и причины отказа; **Consequences** — ограничения и компромиссы выбора; ссылки на canonical contracts и типы. Опускать пустые разделы.
- Поведение, ownership, lifecycle, ошибки и постоянные инварианты задавать один раз в canonical contract. В ADR ссылаться на конкретные разделы, не пересказывать их. Не включать полные постановки будущих задач, тестовые матрицы, копии типов, общие инструкции и историю проверок.
- Dependency Review сохраняет все обязательные критерии §5 AGENTS: компактная таблица, exact versions, датированный verdict и первичные источники. Не вставлять сырые metadata, логи и ход исследования. Подробные доказательства, если нужны для аудита, оставлять в связанной Issue/comment; не делать их обязательным чтением каждого исполнителя.
- Не экономить контекст созданием цепочки дополнительных документов. Каждый факт имеет один источник; остальные места содержат точную ссылку. Не требовать чтения всего ADR или всего набора спецификаций, если задаче нужны отдельные разделы; при неясности границ расширить чтение.

## ARCHITECT RESULT

Общий отчёт `TASK → CHANGES → BOUNDARIES → SPRITES → VERIFICATION → RECOMMENDED NEXT GATE` дополнить содержимым:

- **Decision:** решение и причина, 2–4 предложения.
- **Layer boundaries & Contracts:** затронутые спецификации, объявленные типы и владельцы.
- **Implementation consequences:** короткий список действий, блокеров и проверок именно для связанной задачи; постоянные требования и краевые случаи — точными ссылками на разделы contracts. Для нескольких задач разделить последствия по Task ID, чтобы исполнитель читал свою часть. Явно назвать обязательные источники/разделы; весь связанный результат и применимые последствия остаются обязательными по §12 AGENTS.

Результат должен быть discoverable из связанной Issue/comment или указанного canonical source. Хранить отчёт в одном месте, предпочтительно в Issue/comment; из ADR/контракта дать ссылку, не встраивать копию отчёта. В отчёте ссылаться на принятое решение и контракты, не пересказывать их; VERIFICATION — только итог и незакрытые gates, без логов и хроники. Не загружать исполнителю исследовательские материалы по умолчанию.
