# Правила разработки Project Wisp

Единый свод архитектурных, инженерных и эксплуатационных стандартов проекта Project Wisp. Обязателен для применения во всех задачах, изменениях кодовой базы, тестах и спецификациях.

## 1. Базовые принципы и скоуп

- **Источники требований и scope:**
  - Исполнимый скоуп, критерии приемки и out-of-scope задачи задаются назначенной GitHub Issue;
  - `AGENTS.md` определяет границы репозитория, `docs/engine/*.md` — стабильные контракты подсистем;
  - Запрещены скрытый рефакторинг, смежные оптимизации и реализация будущих фаз вне текущей Issue;
  - Замеченную проблему вне скоупа зафиксируй в отчете, не исправляй скрытно.
- **Автономный Desktop (No-Backend):**
  - В проекте отсутствуют серверный бэкенд, удаленная авторизация, биллинг, прямые AI SDK и API-ключи пользователей;
  - Все AI-взаимодействия изолированы контрактом `IAIProvider` с локальной реализацией по умолчанию (`MockAIProvider`).
- **Запрет сторонних npm-зависимостей:**
  - Добавление любых новых зависимостей в `package.json` запрещено без обязательного предварительного Dependency Review;
  - Допустимо только при отсутствии возможностей стандартных Node.js, Electron и TypeScript API.
- **Минимальный вертикальный срез:**
  - Изменения реализуются минимальным vertical slice с переиспользованием существующих интерфейсов, типов и портов.

## 2. Архитектурные границы (Clean Architecture)

Направление зависимостей строго однонаправленное:
`Renderer -> typed preload / IPC -> Application -> Domain <- Infrastructure (adapters -> ports)`

- **Domain:**
  - Ядро чистой бизнес-логики на чистом TypeScript;
  - Запрещены зависимости от React, Electron, Node.js API, SQLite, сети и `process.platform`.
- **Application:**
  - Содержит use cases, команды, запросы и объявляет интерфейсы портов (`src/application/ports/`);
  - Порт определяется потребителем (Application), адаптер реализуется в Infrastructure;
  - Не зависит от UI-фреймворков и платформенных деталей.
- **Infrastructure:**
  - Реализует порты (`src/infrastructure/`), инкапсулирует вызовы Electron, ОС, файловой системы, SQLite и провайдеров.
- **Main Process:**
  - Владеет жизненным циклом окон, IPC-обработчиками, оркестрацией use cases и DI-композицией компонентов.
- **Принцип Architecture-as-Code (нулевой дрейф контрактов):**
  - При изменении контрактов движков (`docs/engine/*.md`) создание типизированных портов в `src/application/ports/` обязательно до начала разработки адаптеров в `src/infrastructure/`.
- **Размер и содержание контрактов (`docs/engine/*.md`):**
  - Целевой объем файла спецификации движка — 250–400 строк (жесткий лимит — 450 строк);
  - В контрактах фиксируются только DTO, формулы, матрицы переходов FSM и компактные таблицы; запрещено дублирование смежных документов.
- **Разделение подсистем и движков:**
  - `IAIProvider` возвращает семантический DTO и не имеет доступа к React, DOM, стилям и кадрам анимации;
  - Render Engine отвечает за visual props, слои, границы и масштабирование (`docs/engine/RENDER_ENGINE.md`);
  - Animation Engine управляет клипами, приоритетами и прерываниями (`docs/engine/ANIMATION_ENGINE.md`).

## 3. Безопасность Electron и изоляция IPC

- **Конфигурация BrowserWindow:**
  - Обязательны флаги: `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`, `webSecurity: true`, `allowRunningInsecureContent: false`.
- **Изоляция системных вызовов:**
  - В Renderer категорически запрещен доступ к Node.js API (`fs`, `path`, `os`, `child_process`);
  - Запрещено выполнение произвольных shell-команд;
  - Системные данные приложения хранятся строго в стандартных путях (`app.getPath('userData')`).
- **Контроль навигации:**
  - Открытие сторонних окон и непредусмотренные переходы блокируются (`setWindowOpenHandler`, `will-navigate`);
  - Внешние URL проверяются по протоколам/хостам перед вызовом `shell.openExternal`.
- **Контракт Preload (`window.wispAPI`):**
  - Запрещен экспорт сырого `ipcRenderer`, сквозных методов `send/on/invoke` и динамических имен каналов;
  - `window.wispAPI` предоставляет строго типизированные точечные функции под конкретные сценарии;
  - Подписки обязаны возвращать unsubscribe-функцию для явной очистки слушателя при размонтировании.
- **Валидация и передача данных по IPC:**
  - Main-процесс валидирует канал, sender и payload до вызова Application;
  - Через IPC разрешена передача только сериализуемых DTO (plain objects, примитивы, массивы — без методов, классов и циклических ссылок).

## 4. Строгая типизация TypeScript

- **Запрет обхода типов:**
  - Категорический запрет на `any`, `@ts-ignore`, `@ts-nocheck` и необоснованные assertions (`as Type`, `!`);
  - Для внешних и динамических данных использовать `unknown` с проверкой через type guards или схемы валидации.
- **Явные типы на границах:**
  - Все экспортируемые функции, методы, порты, DTO, use cases и IPC-сообщения имеют явные типы аргументов и результатов.
- **Моделирование состояний:**
  - Для FSM-состояний, событий, переходов и результатов с вариантами обязательны discriminated unions;
  - Предпочтение прозрачным предметным типам перед сложными многоуровневыми условными типами.
- **Обработка ошибок и приватность:**
  - Ошибки внешних границ преобразуются в типизированный Result или контролируемый fallback (запрещено проглатывать исключения);
  - Запрещено логировать приватные данные памяти, секреты и сырой пользовательский ввод.

## 5. Управление состоянием, данными и памятью

- **Владение состоянием:**
  - *Local UI state:* локальное состояние React (фокус, hover, ввод текста);
  - *Presentation state:* глобальный store Renderer (Zustand) только для визуальных данных, разделяемых компонентами;
  - *Domain / FSM state:* управляется исключительно в Main и Application;
  - *Persistent state:* доступен только через порты репозиториев; запрещено дублировать доменный стейт в несколько конфликтующих сторов.
- **База данных (SQLite):**
  - Доступна только в Main/Infrastructure через порты (например, `IMemoryRepository`, `ISettingsRepository`);
  - Любые изменения схемы оформляются детерминированными транзакционными миграциями с контролем через `PRAGMA user_version`;
  - Именование таблиц и столбцов — `snake_case`. Даты сохраняются в формате UTC ISO-8601.
- **Приватность и очистка памяти:**
  - Память локальна и нейтральна к AI-провайдеру;
  - Полная очистка памяти обязана физически удалять историю, факты, суммаризации и снапшоты без устаревших кэшей.

## 6. React Renderer и пользовательский интерфейс

- **Чистое представление:**
  - Компоненты получают готовые presentation props и отправляют intents через `window.wispAPI`;
  - В коде React запрещены физические расчеты, принятие решений по FSM, сохранение данных и сырые ответы провайдера.
- **Жизненный цикл эффектов:**
  - Каждый `useEffect` с таймером, IPC-слушателем или браузерным событием обязан иметь полный список зависимостей и cleanup-функцию.
- **Производительность прозрачного окна:**
  - Запрещены тяжелые полноэкранные CSS-фильтры, размытия и составные тени, нарушающие оконный композитинг и роняющие FPS.
- **Debug UI:**
  - Оверлеи отладки не должны отображать чувствительные факты памяти или сырые приватные структуры.

## 7. Кроссплатформенность и Desktop-интеграция

- **Изоляция платформенной специфики:**
  - Поддерживаемые платформы: Linux (Ubuntu как базовая среда), Windows, macOS;
  - Использование `process.platform` разрешено исключительно внутри платформенных адаптеров `src/infrastructure/`.
- **Работа с путями и файловой системой:**
  - Пути формируются строго через `path.join / resolve / normalize` и `app.getPath(...)`;
  - Запрещена ручная конкатенация строк путей. Регистр символов в import обязан точно совпадать с файловой системой.
- **Оконная интеграция:**
  - Поведение окна (always-on-top, click-through, трей, автозапуск) реализуется через адаптеры;
  - Для Linux обязательны безопасные fallbacks под особенности Wayland и X11;
  - Неподдерживаемая функциональность ОС обязана давать безопасный fallback, а не приводить к падению приложения.

## 8. Верификация, тестирование и Quality Gates

- **Обязательный Gate перед коммитом:**
  - `npm run typecheck` — строгая проверка типов перед фиксацией изменений; коммит с ошибками типов категорически запрещен;
  - `npm test` — запуск набора модульных и интеграционных тестов для любого продуктового кода.
- **Проверки по уровню риска:**
  - Изменение сборочных путей, Vite/Electron конфигурации, packaging: запуск `npm run build`;
  - Использовать только скрипты, существующие в `package.json` (не объявлять несуществующие lint gates);
  - Для docs-only изменений проверяются корректность ссылок и чистота diff, продуктовые тесты не требуются.
- **TDD и рефакторинг:**
  - Bugfix требует воспроизведения бага и написания падающего регрессионного теста до внесения исправлений;
  - Рефакторинг сохраняет поведение, проводится при наличии тестов и не смешивается с добавлением новой функциональности;
  - Итоговый отчет исполнителя фиксирует: scope (`TASK`), изменения (`CHANGES`), границы (`BOUNDARIES`), верификацию (`VERIFICATION`), следующий шаг (`RECOMMENDED NEXT GATE`).
