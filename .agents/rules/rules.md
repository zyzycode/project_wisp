# RULES: Project Wisp Core Guidelines

Данный документ объединяет все базовые правила разработки, архитектурные ограничения, стандарты качества и процессные соглашения Project Wisp.

---

## 1. Автономность и среда исполнения
- **Desktop Offline-First:**
  - Project Wisp — локальное настольное приложение (Electron + React + TypeScript);
  - Запрещено добавление серверных прослоек, backend-сервисов, внешних БД, удаленных API (за исключением прямого вызова LLM через `IAIProvider`);
  - Все состояние хранится локально (SQLite / config files).
- **Платформенная нейтральность:**
  - Базовая платформа — Linux (Ubuntu / Wayland / X11); целевые — Windows и macOS;
  - Запрещен платформозависимый код (`process.platform`, специфичные пути) в Domain, Application и UI слоях;
  - Любая специфика ОС изолируется в `src/infrastructure/platform/` за общими портами (`IPlatformAdapter`).

---

## 2. Архитектура и границы слоев (Clean Architecture)
- **Domain:**
  - Содержит чистую бизнес-логику, математику, FSM поведения, состояние персонажа (Needs, Mood), кинематику и правила анимации;
  - Полная изоляция: запрещены импорты из React, Electron, Node.js (`fs`, `path`, `os`), SQLite, UI и AI SDK;
  - Детерминированность: время, случайные числа и внешние события передаются только как явные параметры.
- **Application:**
  - Содержит use cases, команды, запросы и объявляет интерфейсы портов (`src/application/ports/`);
  - Порт определяется потребителем (Application), адаптер реализуется в Infrastructure;
  - Не зависит от UI-фреймворков и платформенных деталей.
- **Infrastructure:**
  - Реализует порты (`src/infrastructure/`), инкапсулирует вызовы Electron, ОС, файловой системы, SQLite и провайдеров.
- **Main Process:**
  - Владеет жизненным циклом окон, IPC-обработчиками, оркестрацией use cases и DI-композицией компонентов.
- **Принцип Architecture-as-Code (нулевой дрейф контрактов) и разделение ролей:**
  - **Зона Architect:** Архитектор проектирует архитектуру подсистем, формулирует инварианты, модели и таблицы переходов в `docs/engine/*.md` (без раздувания простыней кода) и объявляет целевые контракты в кодовой базе (типизированные интерфейсы портов в `src/application/ports/` и DTO в `src/shared/ipc-contracts.ts`).
  - **Зона App Developer:** На Fast-Track разработчик самостоятельно объявляет и расширяет порты в `src/application/ports/` и DTO в `src/shared/ipc-contracts.ts`, либо реализует логику, сервисы, адаптеры в `src/infrastructure/`, UI в `src/renderer/` и тесты на базе спроектированных архитектором контрактов.
  - Объявление типизированных портов в `src/application/ports/` и DTO в `src/shared/ipc-contracts.ts` обязательно до начала разработки адаптеров и сервисов.
- **Размер и содержание контрактов (`docs/engine/*.md`):**
  - Целевой объем файла спецификации движка — 250–400 строк (жесткий лимит — 450 строк);
  - В контрактах фиксируются только концепции, инварианты, формулы, матрицы переходов FSM и компактные таблицы со ссылками на типы в коде; запрещено дублирование смежных документов и раздувание псевдокода.
- **Разделение подсистем и движков:**
  - `IAIProvider` возвращает семантический DTO и не имеет доступа к React, DOM, стилям и кадрам анимации;
  - Render Engine отвечает за visual props, слои, границы и масштабирование (`docs/engine/RENDER_ENGINE.md`);
  - Animation Engine управляет клипами, приоритетами и прерываниями (`docs/engine/ANIMATION_ENGINE.md`).

## 3. Безопасность Electron и изоляция IPC
- **Настройки BrowserWindow:**
  - `contextIsolation: true` — обязательно для всех окон;
  - `nodeIntegration: false` — категорически запрещено включать Node.js в Renderer;
  - `sandbox: true` — включен по умолчанию.
- **IPC через Preload:**
  - Renderer общается с Main исключительно через типизированный мост `window.wispAPI`, экспонируемый в `src/preload/`;
  - Запрещен прямой вызов `ipcRenderer.send/invoke` со произвольными строковыми каналами из React-компонентов;
  - Все входные данные IPC валидируются в Main-процессе перед обработкой.
- **Сетевая безопасность:**
  - Renderer не выполняет произвольных сетевых запросов;
  - Внешние вызовы (AI провайдеры) выполняет только Main-процесс.

---

## 4. UI и Renderer слой
- **Тупой UI (Dumb UI):**
  - React-компоненты отвечают только за отображение текущего состояния (`presentation state`) и трансляцию действий пользователя в IPC;
  - Вся бизнес-логика, расчет координат, физика и FSM живут в Domain/Main.
- **Производительность:**
  - Избегать лишних ререндеров тяжелых визуальных компонентов;
  - Анимации используют `requestAnimationFrame` или CSS transforms (`transform: translate3d(...)`);
  - Изменение позиции окна выполняется через IPC-батчинг, а не попиксельные частые синхронные вызовы.

---

## 5. Зависимости (Dependency Policy)
- **Zero New Dependencies First:**
  - Предпочтение собственным минималистичным решениям на чистом TypeScript перед добавлением библиотек;
  - Новая npm-зависимость требует явного согласования (Dependency Review).
- **Критерии допустимости:**
  - Не тащит за собой нативные C++ биндинги (если нет крайней необходимости);
  - Поддерживает ESM/TypeScript без костылей;
  - Имеет активный maintenance, минимальный вес и нулевые уязвимости (`npm audit`).

---

## 6. Качество кода и TypeScript
- **Строгая типизация (Strict Mode):**
  - Никаких `any` (использовать `unknown` с type guards);
  - Никаких `as unknown as Type` (двойных приведений) и подавления ошибок через `@ts-ignore` (допустим `@ts-expect-error` только с обязательным комментарием причины);
  - Строгие типы для всех IPC сообщений, событий и доменных сущностей (`readonly` свойства по умолчанию).
- **Code Style & Чистота:**
  - Имена функций и переменных явно отражают намерение;
  - Никаких неиспользуемых импортов, переменных и мертвого кода;
  - Файлы организованы логично: не превышать разумный размер (целевой — до 300 строк на файл реализации).

---

## 7. Процесс разработки и Fast-Track
- **Fast-Track (по умолчанию):**
  - Обычные задачи разработки, рефакторинга, багфиксов и эволюционного расширения портов/DTO берет `app-developer` напрямую;
  - `architect` привлекается **только** по 4 триггерам (новая подсистема, сдвиг IPC-границ, новая npm-зависимость, тупик/конфликт контрактов).
- **Итеративность и фокусировка (YAGNI):**
  - Решать только задачу в скоупе текущего Task ID / Issue;
  - Запрещено выполнять попутный рефакторинг не связанных подсистем («заодно почистил»);
  - Не проектировать абстракции про запас («на будущее»).

---

## 8. Тестирование и верификация (Verification Gates)
- **Обязательный Gate перед коммитом:**
  - `npm run typecheck` — строгая проверка типов перед фиксацией изменений; коммит с ошибками типов категорически запрещен;
  - `npm test` — запуск набора модульных и интеграционных тестов для любого продуктового кода логики, адаптеров и UI.
- **Проверки по уровню риска:**
  - Изменение сборочных путей, Vite/Electron конфигурации, packaging: запуск `npm run build`;
  - Использовать только скрипты, существующие в `package.json` (не объявлять несуществующие lint gates);
  - **Архитектурные задачи с контрактами (`owner: architect`):** обязателен запуск `npm run typecheck` (гарантия компилируемости добавленных/изменённых портов и DTO в `src/`), проверка ссылок markdown и лимитов строк документации; продуктовые тесты не требуются до реализации логики;
  - **Задачи реализации (`owner: app-developer`):** обязателен запуск `npm run typecheck && npm test`;
  - **Для чисто текстовых docs-only изменений (README, гайды):** проверяются корректность ссылок и чистота diff, запуск тестов не требуется.
- **Автономный цикл реализации (Autonomous Delivery Loop):**
  - Роли `architect`, `app-developer` и `reviewer` взаимодействуют напрямую внутри цикла задачи (`implementation/fixes <-> review`) без передачи промежуточных шагов менеджеру проекта;
  - `project-manager` подключается только после завершения задачи (`Approved` / `done`) для коммита, закрытия Issue и запуска следующей задачи.
- **TDD и рефакторинг:**
  - Bugfix требует воспроизведения бага и написания падающего регрессионного теста до внесения исправлений;
  - Рефакторинг сохраняет поведение, проводится при наличии тестов и не смешивается с добавлением новой функциональности;
  - Unit-тесты изолированы: моки для внешних адаптеров, никаких реальных таймеров без vitest fake timers.
