# 60-testing.md — Стандарты тестирования и верификации

Правила написания тестов и обеспечения качества кодовой базы Project Wisp.

---

## 1. Пирамида тестирования в проекте

1. **Unit Tests (Основа пирамиды — высокий приоритет):**
   - Доменная логика: стейт-машина поведения (`BehaviorStateMachine`), стейт-машина анимаций (`AnimationStateMachine`).
   - Расчёт физики и геометрии: координаты, границы экранов, коллизии.
   - Парсинг и форматирование данных, DTO, адаптеры DTO.
   - Изолированные утилиты и чистые функции.
2. **Integration Tests (Средний приоритет):**
   - Взаимодействие Use Cases с репозиториями SQLite (на базе `:memory:` SQLite БД).
   - Логика `MockAIProvider` и оркестрация ответов.
   - IPC-роутинг и контракты сериализации.
3. **UI / Component Tests (Низкий/выборочный приоритет):**
   - Только критические интерактивные компоненты (например, форма ввода чата, переключение состояний).
   - Не тестировать визуальные стили, пиксели и CSS-транзишены автотестами.

---

## 2. Что тестировать ОБЯЗАТЕЛЬНО
- Ключевые сценарии переходов в `BehaviorStateMachine` и `AnimationStateMachine`, включая interrupt/priority cases.
- Обработка граничных случаев (выход за пределы экрана, нулевая скорость, пустые сообщения).
- Fallback-поведение при ошибках `IAIProvider`.
- Миграции базы данных SQLite (применение миграций с $V_0$ до $V_n$).
- Acceptance criteria назначенной GitHub Issue.

---

## 3. Что тестировать НЕ СТОИТ (Do Not Test)
- ❌ Сторонние библиотеки и Electron API (не нужно тестировать, что `BrowserWindow.create()` создаёт окно).
- ❌ Простые геттеры, сеттеры и тривиальные обёртки.
- ❌ Статические CSS-файлы и макеты.
- ❌ Внутренние приватные методы (тестируйте через публичный интерфейс класса/модуля).

---

## 4. Обязательный чек-лист верификации после завершения задачи
Перед тем как считать product-code задачу выполненной, запустите проверки, соответствующие риску изменения:

```bash
# 1. Проверка типов TypeScript
npm run typecheck # (или npx tsc --noEmit)

# 2. Проверка стиля и линтера
npm run lint

# 3. Запуск тестов
npm test
```

Если обнаружена хоть одна ошибка — исправьте её до отправки отчёта пользователю.

Docs-only задачи проверяются через markdown/diff consistency и не требуют запуска product tests, если пользователь, Project Manager или конкретный workflow не попросили иначе.

Reviewer работает по конкретному test/verification gate из GitHub Issue и возвращает Project Manager-у `PASS`, `FAIL` или `BLOCKED` с recommended next gate.
