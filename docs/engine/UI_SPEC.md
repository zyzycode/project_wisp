# UI / Renderer — намерения

> **Статус: intent brief, не архитектурный контракт.**
> Документ фиксирует только желаемый пользовательский результат. Перед задачами на реализацию `architect` должен сверить текущий код и действующие engine contracts, принять архитектурные решения и заменить этот черновик компактным согласованным контрактом.

## Продуктовые намерения

- Wisp остаётся прежде всего персонажем на рабочем столе, а интерфейс поддерживает взаимодействие с ним, не превращаясь в обычное большое приложение.
- Пользователь может видеть состояние и реакции персонажа, взаимодействовать с ним мышью, начать диалог и открыть доступные действия или настройки.
- Реплики, меню и другие временные элементы не должны скрывать персонажа или обрезаться границами окна и экрана.
- Основной сценарий должен быть понятен без знания AI-провайдеров, моделей, токенов и внутреннего устройства приложения.
- Пользовательский UI и инструменты разработки должны быть визуально и функционально разделены.
- Поведение должно оставаться пригодным для Linux, Windows и macOS.

## Намерения по границам

- Renderer отображает подготовленное состояние и отправляет пользовательские действия через типизированную Preload-границу.
- Renderer не владеет физикой движения, domain-решениями, persistence, provider logic или платформенной спецификой.
- Render Engine определяет, как визуальное состояние превращается в слои и кадры; UI размещает результат и интерактивные поверхности.
- Точные владельцы состояния, DTO, IPC events и механика изменения окна этим черновиком не устанавливаются.

## Что пока не определено

- дерево и названия React-компонентов, hooks и каталогов;
- состав и сигнатуры `window.wispAPI`, IPC DTO и событий;
- точный набор действий меню, настройки и поведение чата;
- правила размещения временных элементов возле границ экрана;
- визуальный стиль, размеры, анимационные тайминги и accessibility behavior;
- состав debug UI и способ его включения;
- стратегия UI-тестов и desktop smoke checks.

## Задача для Architect

`architect` должен:

1. Проверить текущие Main, Preload и Renderer implementation boundaries и не описывать несуществующую структуру как готовую.
2. Сверить решения с `.agents/rules/10-architecture.md`, `docs/engine/RENDER_ENGINE.md` и другими действительно затронутыми контрактами.
3. Определить минимальную типизированную границу Renderer ↔ Preload ↔ Main, владельцев состояния и допустимые направления событий.
4. Разделить UI, render, domain и platform responsibilities без дублирования соседних engine contracts.
5. Зафиксировать только межслойные решения, необходимые implementer-агентам; локальные детали компонентов оставить реализации.
6. Вынести нерешённые продуктовые вопросы и implementation slices в GitHub Issues.
7. После согласования заменить этот intent brief компактным UI contract и обновить индекс `docs/engine/README.md`.

До выполнения этого architect gate документ нельзя использовать как готовую инструкцию для `app-developer`.
