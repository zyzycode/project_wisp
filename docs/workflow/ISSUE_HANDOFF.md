# Шаблоны менеджера

Справочник для `project-manager`: читать нужный раздел только перед созданием Issue, выдачей или закрытием спринта. Полномочия и маршрутизация — в [инструкции роли](../../.agents/agents/project-manager/agent.md), инварианты/verification — в [AGENTS.md](../../AGENTS.md).

## Создание Issue

- Сначала проверить дубли и readiness. Title: `[<Task ID>] <понятный результат>`, без сложных аббревиатур, роли или статуса.
- Ровно один label `owner:*`; существующие `phase:*`, `track:*`, `area:*`, `needs:architect` — по факту. Новые labels без необходимости не создавать. `documentation` — только для текста, не для типов/контрактов в коде.
- Assignee оставить пустым. Добавить Issue в Project и проверить Status/Priority: `Ready` после readiness, `Blocked` с конкретной причиной при зависимости, `In progress` только при начале работы.
- **Принцип Human-First:** Описание должно быть понятно человеку без архитектурного словаря. Запрещено писать сплошным нагромождением канцелярита и терминов. Обязательны простой человеческий смысл в начале и наглядный пример сценария.
- Тело — до 30–50 строк, до 3–5 ключевых файлов. Task ID/phase/owner и общие правила AGENTS в теле не повторять.

```markdown
## Что делаем (простыми словами)
<1–2 простых предложения без канцелярита: в чём суть фичи, зачем она нужна и что меняется для пользователя.>

## Пример сценария / Как это выглядит
- **Действие:** <например: Пользователь говорит «...» / кликает по окну / наступает таймер>
- **Поведение:** <что конкретно персонаж делает, говорит или показывает на экране>

## Технический Scope (для исполнителя)
- **Целевые файлы:** <до 3–5 ключевых файлов или модулей>
- **Контракты:** <точные ссылки на разделы канонических спецификаций>
- **Архитектурное решение:** <ссылка на комментарий в Issue при наличии>

## Критерии приёмки
- [ ] <Проверяемое поведение / артефакт>
- [ ] <Краевой случай / поведение при ошибке или перезапуске>

## Ограничения и Out of Scope
- <Что явно НЕ входит в эту задачу и что НЕЛЬЗЯ менять>
- <Явные зависимости / блокеры>

## Verification
<Gate из §11 AGENTS по роли и типу изменений>
```

Одна фича — один законченный vertical slice; связанные методы/DTO не разбивать на отдельные tickets без причины. Для architect-задачи реализация логики/UI вне scope.

## Batch handoff

На каждую из 2–4 задач: `[Task ID] Title`, scope в 1–2 предложениях, ключевые файлы, нужные разделы contracts и `Контекст: текущий чат | новый чат` с краткой причиной. Затем промпт исполнителя без повторения полного текста Issue/AGENTS.

**Исполнитель:**

```text
Ты агент <owner-role>. Прочитай .agents/agents/<owner-role>/agent.md, если её ещё нет в контексте. Выполни <Task ID> по актуальной Issue <полный URL>, соблюдая AGENTS.md, scope и связанные architect decisions. Контекст: <целевые файлы и разделы>. Выполни обязательные проверки и представь отчёт о результате.
```

## Закрытие

После завершения/done и task-scoped коммита: закрыть Issue, проверить фактический `Done` в Project и оставить короткий receipt. Без проверки не заявлять об изменении статуса.

```markdown
## Result — <YYYY-MM-DD>
- Commit: <hash>
- Completion signal: <done | готово>
- Status: Done
```
