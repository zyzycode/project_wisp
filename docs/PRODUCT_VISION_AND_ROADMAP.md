# Wisp: продуктовые решения и roadmap

Решения пользователя от 2026-09-08–18; редакционная сверка структуры репозитория — 2026-10-13. Документ сохраняет продуктовые цели, а не статусы задач или разрешения на инженерные изменения. Задачи и зависимости — в [GitHub Issues](https://github.com/zyzycode/project_wisp/issues) и [Project](https://github.com/users/zyzycode/projects/1); технические правила — в [engine contracts](../frontend/docs/engine/README.md).

## 1. Центральная идея

Wisp — ИИ-персонаж с собственной инициативой, который живёт на рабочем столе как полноценный шимеджи. Основная ценность — индивидуальность, общение, действия и развитие отношений с конкретным пользователем.

Ключевое пожелание пользователя:

> У персонажа должна быть устойчивая личность, которая постепенно подстраивается под пользователя в своих пределах. Она может знать, что хочет от неё пользователь, и в зависимости от характера подыгрывать ему или наоборот.

Персонаж должен понимать, как нравиться пользователю, сохраняя собственную инициативу и ограничения характера. Просьба «веди себя как цундере» сообщает о желании пользователя; она не должна автоматически навсегда переписывать личность.

## 2. Подтверждённые продуктовые решения

| Область | Решение пользователя |
|---|---|
| Первый персонаж | Один персонаж: милая девочка-помощник. Точная стартовая личность менее важна, чем развитие через общение; использовать существующие базовые статы как отправную точку. |
| Авторство личности | Готовые авторские личности; пользователи не создают собственных. В первой версии — один персонаж. |
| Индивидуальность | У каждого пользователя своя развивающаяся версия персонажа, собственная история и отношения. |
| Адаптация | Всё может постепенно меняться, кроме фундаментальных ограничений. Существующие caps должны сохраняться. Пример пользователя про «70 баллов» иллюстрирует границу, а не задаёт новое числовое правило. |
| Самостоятельность | Полная самостоятельность в рамках возможностей персонажа, но без назойливости. Может сам начинать взаимодействие. |
| Несогласие | Допустимы споры, подколы, отказ подыгрывать и обида; персонаж задуман как автономная личность. |
| Память | Факты о пользователе, предпочтения, обещания, важные события, общие шутки и история отношений. |
| Память MVP | Локальная SQLite — основное хранилище индивидуальной памяти и изменяемого состояния персонажа. Первый вариант — без эмбеддингов и векторной БД. |
| Расширяемость памяти | Архитектурно сохранить возможность добавить семантический поиск позднее, без замены личности и потери накопленной истории. Конкретные технологии и размещение будущего индекса не выбраны. |
| Разговорная модель | Локальная LLM на клиенте не рассматривается; разговорный ИИ вызывается через собственный backend у внешнего провайдера. |
| Редактирование | Пользователь не должен менять файлы персонажа. Редактор личности не запрошен; конкретные средства исправления и удаления памяти ещё не согласованы. |
| Наблюдение | Разговор, взаимодействия с персонажем, активные приложения, заголовки окон и содержимое экрана входят в желаемые возможности. |
| Локальное распознавание | Пользователь допускает небольшую локальную модель / обработку изображений, упоминал OpenCV как идею. Конкретная технология не выбрана. |
| Действия | Перемещаться, играть на рабочем столе и напоминать о делах. |
| Общение | Сначала короткие реплики в облачке. Расширяемое облачко и голос — возможное дальнейшее развитие, не обязательства первой версии. |
| Offline | Без интернета достаточно автономного шимеджи с заготовленным поведением и репликами, без разговорного ИИ. |
| Backend | Собственный сервер оркестрирует API-провайдеров и формирует AI-ответ. Текущий Python/FastAPI backend находится в `backend/`; возможности и пробелы — в [серверном навигаторе](../backend/docs/README.md). |
| Передача данных | Допустимо отправлять выбранные воспоминания на свой сервер и API-провайдеру. Это не решение отправлять всю БД или непрерывно передавать экран. |
| Авторизация и перенос | В дальнейшем нужна авторизация, чтобы продолжать взаимодействие с персонажем; перенос состояния между устройствами — позже. |
| Первый запуск | Небольшая группа тестеров, продукт и его тестирование ориентированы на Windows. Linux не входит в продуктовый scope. Умеренные требования к железу; числовые ограничения пока не заданы. |
| Монетизация | Пользователь платит, продукт выделяет ему бюджет токенов. В бесплатной версии — максимально скромные бюджеты. Цены и лимиты не определены. |

Тип отношений (дружба, романтика и т. п.) отдельно не определён. Ответ пользователя: персонаж должен быть умным и понимать, каким быть, чтобы нравиться пользователю. Не считать это автоматическим согласованием всех видов отношений.

## 3. Сценарий, выражающий ценность продукта

Персонаж пытается поймать курсор и говорит:

> «Стой, я почти поймала!»
>
> «Ты там играть со мной вздумал?»

При успехе и неудаче должны быть разные реплики и действия. Пользователю важны полный набор соответствующих анимаций, знание того, во что он играет, и его предпочтений.

Предлагаемый первый законченный сценарий:

1. Персонаж замечает возможность игры и по собственной инициативе начинает взаимодействие.
2. Преследует курсор и пытается поймать его в рамках доступной физики и поверхностей.
3. Локальный движок определяет реальный исход: поймала, промахнулась, потеряла цель или прекратила игру.
4. Реплика и анимация соответствуют исходу, характеру и текущему состоянию.
5. Персонаж прекращает инициативу, если пользователь не поддерживает её.
6. Значимый совместный опыт сохраняется и учитывается после перезапуска.
7. В дальнейших взаимодействиях учитываются накопленные предпочтения пользователя.

Это критерий направления, а не утверждение о текущей готовности.

## 4. Текущая база и ограничения

Desktop и backend находятся в одном репозитории, но запускаются независимо: [ADR-017](adr/ADR-017-monorepo.md). Локальные FSM, физика, память и ввод принадлежат desktop; backend возвращает разрешённые семантические предложения. Потеря сети не останавливает локальную жизнь.

В desktop есть SQLite persistence, явные знания, bounded recall, адаптация и клиентские режимы API v1/v2/v3. Это наличие реализации, не подтверждение ручной приёмки. Семантика и ограничения — в [Memory](../frontend/docs/engine/MEMORY_ENGINE.md), [Character](../frontend/docs/engine/CHARACTER_ENGINE.md), [AI Provider](../frontend/docs/engine/AI_PROVIDER_CONTRACT.md) и [AI Events](contracts/AI_EVENTS_CONTRACT.md).

**Встроенный backend поддерживает только v1 chat/touch.** В нём отсутствуют v2/v3 и часть согласованных серверных safeguards: [актуальные gaps](../backend/docs/README.md#фактическая-реализация). Более поздняя отдельная серверная поставка описана в [историческом BE-P01](../backend/docs/archive/BE_P01_RESULT.md); она не импортирована целиком и не доказывает готовность текущего сервера или deployment.

Продуктовый запуск ориентирован на Windows. Существующие Linux/macOS adapters и capability fallback сохраняются по [инженерным правилам](../frontend/AGENTS.md); расширение приёмки на эти платформы не входит в ближайший продуктовый этап.

## 5. Ближайшие этапы и критерии MVP

| Этап | Проверяемый результат |
|---|---|
| Приёмка локального персонажа | Запуск, ввод, drag, сон, игра и согласованные реакции проходят [Windows checklist](../frontend/docs/WINDOWS_MVP_CHECKLIST.md); память переживает restart и корректно очищается. |
| Совместимость серверной поставки | Устранены документированные gaps текущего backend; версии, fixtures, бюджеты, ошибки и lifecycle соответствуют принятым контрактам. Перед выдачей задачи сверить существующий код и backlog, включая историческую внешнюю поставку. |
| Сквозной диалог с памятью | На совместимом backend исправленные факты, допустимые игровые эпизоды и индивидуальное состояние используются после restart; временная роль не переписывает личность. |
| Инициативы и адаптация | Реальный исход игры согласован с речью и действиями; разные истории дают уместные различия, инициативы остаются ненавязчивыми. |
| Допуск тестеров | Проверены доступ, политика передачи/удаления данных и серверный расход; измерены CPU/RAM, задержка и стоимость. Числовые пределы ещё нужно согласовать. |

Потеря сети, timeout и исчерпание бюджета сохраняют локальное поведение. Некорректные и поздние ответы после reset/dispose не меняют состояние и не возвращают удалённую память. Автоматические проверки и закрытие Issue не заменяют ручную приёмку; результат записывается для конкретной версии и окружения.

## 6. Дальнейшее развитие и открытые решения

- Оценить качество bounded recall в длительных разговорах. При подтверждённых пропусках отдельно проектировать семантический/гибридный поиск: индекс производен от исходных записей, его замена не должна терять историю. Эмбеддинги, модель и размещение индекса не выбраны и не блокируют первый MVP.
- Согласовать выражение несогласия/обиды и допустимые виды отношений; проверить темп адаптации в реальных сессиях. Эмоциональные реакции не должны мешать закрытию приложения и отключению инициатив — это продуктовый ориентир для дальнейшей детализации.
- Определить пользовательский интерфейс исправления/удаления памяти, обещания и напоминания. Для напоминаний отдельно задать сроки, часовые пояса, пропущенные события и повторы.
- Наблюдение развивать от активного приложения/заголовков к отдельному эксперименту с экраном. Разрешения, пауза, частота анализа, передаваемые данные и retention требуют решения до реализации; частое использование приложения не доказывает симпатию пользователя.
- Авторизация, тарифы и платёжные права — отдельный этап. Синхронизация требует выбора источника истины, идентичности персонажа, разрешения конфликтов и удаления серверных копий.
- Голос, полноценная синхронизация и массовый публичный запуск отложены. Создание пользователем персонажей не запрошено.

## 7. Направление развития: Context/Prompt Engine

Решение пользователя от 2026-10-13: использовать идею и подходящие части готовой реализации Context/Prompt Engine из SillyTavern **в рамках существующей архитектуры Wisp**. Владелец проекта разрешил заимствование и адаптацию кода с учётом его лицензии. Это продуктовый ориентир для развития prompting, а не утверждение о готовой реализации. Референсы: [исходный код](https://github.com/SillyTavern/SillyTavern), [Prompt Manager](https://docs.sillytavern.app/usage/prompts/prompt-manager/), [World Info](https://docs.sillytavern.app/usage/core-concepts/worldinfo/), [Character Design](https://docs.sillytavern.app/usage/core-concepts/characterdesign/). При реализации сначала изучить существующие алгоритмы и выбрать пригодные части для переноса/адаптации к Python backend; зафиксировать исходные файлы/commit, лицензию и изменения, сохранить применимые уведомления. Основная лицензия SillyTavern — [AGPL-3.0](https://github.com/SillyTavern/SillyTavern/blob/release/LICENSE). Перенос всего приложения или его runtime не требуется.

Желаемый Context/Prompt Engine собирает запрос из отдельных управляемых блоков:

| Блок | Назначение |
|---|---|
| Character Profile | Авторское ядро, манера общения и фундаментальные ограничения персонажа. |
| Примеры диалогов | Собственные примеры желаемого стиля; явно отделены от реальной истории пользователя. |
| Lore / World Info | Выбранные сведения о персонаже и его мире по релевантности; не вся библиотека в каждом запросе. |
| Текущий mood/state и события | Актуальный снимок состояния и реальные desktop outcomes; модель не выдумывает физический результат. |
| Long-term memory | Только релевантные разрешённые факты и эпизоды с происхождением и актуальными исправлениями. |
| Summary и недавний диалог | Производное резюме старых разговоров вместе с недавними репликами; summary не заменяет исходные записи и не имеет приоритета над исправленным фактом. |
| Token budget | Бюджет входного контекста с резервом на ответ, приоритетами блоков и детерминированным сокращением. Это не тарифы и не платёжные права. |
| Provider/model templates | Преобразование общего контекста в поддерживаемые роли, формат и ограничения конкретного API/модели. |

Desktop продолжает владеть индивидуальной памятью, изменяемым CharacterState и локальным поведением, выбирает разрешённый контекст через существующие Application ports. Backend собирает prompt из переданного контекста и серверных инструкций; provider adapter применяет формат конкретного API. Профиль в prompt описывает тот же авторский характер и его ограничения. Новое серверное хранение памяти, перенос личности и behavior planner в это направление не входят. Владение определяется действующими [Memory](../frontend/docs/engine/MEMORY_ENGINE.md#1-границы-владение-и-источник-истины), [Character](../frontend/docs/engine/CHARACTER_ENGINE.md#владение) и [wire memory](contracts/BACKEND_MEMORY_CONTRACT.md#4-данные-и-удаление).

LLM не получает прямое управление ОС. Backend и клиент независимо валидируют разрешённые speech/intents/emotions; это семантические предложения, а не команды ОС или произвольная запись числового состояния. Конкретный набор полей и endpoint-specific ограничения определяет wire contract: например, существующий v3 events остаётся text-only. История, память и наблюдения не могут переопределять системные ограничения; примеры и lore не выдаются за факты о пользователе.

Развивать поэтапно: сначала выделить блоки существующего prompt и правила их приоритета/бюджета, затем добавлять собственные примеры, релевантный lore и summary по отдельным задачам. Новые данные не добавляются неявно в существующий wire; расширения должны учитывать обе стороны API и правила передачи/удаления. Для summary отдельно определить источник, исправление/инвалидацию после удаления памяти, стоимость и момент генерации: действующий MVP не разрешает фоновые summary-вызовы. Приёмочные сценарии проверяют сохранение характера, использование исправленного факта, переполнение контекста и поздний ответ после reset. Architect gate применяется только при триггерах общих правил, а не из-за названия Context/Prompt Engine.

Аккаунты, тарифы, межустройственная синхронизация и весь голосовой scope отменены на текущем этапе по решению пользователя от 2026-10-13 (#71–#74); это предложение их не возобновляет. Сборка контекста может развиваться независимо от них.

Графику предоставляет внешний художник-человек. Готовые клипы проверяются по manifest; недостающие ключи и fallback фиксируются в отчёте задачи по [desktop-правилам](../frontend/AGENTS.md#ассеты-и-проверки). Новые инженерные исключения требуют собственного поручения; исторические разрешения из [архива](archive/README.md) не действуют на новые задачи.
