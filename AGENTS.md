# AGENTS: Project Wisp

Общие правила монорепозитория; инструкции ролей и каталогов дополняют их без дублирования и ослабления. Desktop — [frontend/AGENTS.md](frontend/AGENTS.md), backend — [backend/AGENTS.md](backend/AGENTS.md). Для корневого desktop tooling читать desktop-правила, для общей документации — правила затронутых частей.

## 1. Приложения, владение и платформа

Desktop (`frontend/`) и Python/FastAPI backend (`backend/`) имеют отдельные runtime, зависимости, тесты и запуск; backend-код — только в `backend/`.

- Desktop владеет FSM, Needs/Mood, физикой, анимациями, presentation и вводом.
- Backend владеет серверными API, интеграциями, хранением и формированием AI-ответа; возвращает только разрешённые семантические DTO и не управляет локальным runtime.
- Прямые импорты между runtime и перенос бизнес-решений в Renderer запрещены.

Offline-first относится к локальному runtime персонажа и локальным данным desktop (SQLite/config files). Сетевые функции могут требовать подключения; недоступность backend не останавливает локальные FSM, Motion и ввод.

## 2. Архитектура и контракты

- Клиентские use cases используют Application ports; транспорт и auth инкапсулируют Infrastructure adapters, создаваемые Main. Для AI допустимы backend-backed `IAIProvider` и прямой LLM-вызов.
- До реализации сетевой функции определить обе стороны API, валидацию, ошибки, auth, deadline/cancellation, retry/idempotency и поведение при потере связи. Серверный wire contract отделён от локальных Application ports и IPC DTO; ответ валидируется и преобразуется адаптером до использования Application.
- В Alpha desktop и backend обновляются совместно: один API под `/v1`, без wire-поля `version`, поддержки старых клиентов и миграционных адаптеров. Версионирование API — отдельная задача при переходе к независимому обновлению клиентов. Валидация, ошибки и таймауты обязательны. Версии локальных данных и revision карточки персонажа этим правилом не ограничены.
- До передачи или серверного хранения данных определить разрешённый состав, владельца/source of truth, сроки хранения и удаление. Для sync задать разрешение конфликтов и восстановление после разрыва связи. Локальная очистка не означает удаление серверной копии.
- Канонические desktop engine-спецификации — в [frontend/docs/engine/](frontend/docs/engine/README.md), общие API-контракты — в [docs/contracts/](docs/contracts/README.md), wire fixtures — в `docs/contracts/fixtures/`. Python-схемы и TypeScript-типы не импортируют друг друга; fixtures проверяют совместимость.
- При конфликте спецификации и реализации не выбирать удобную версию: остановить затронутую часть и запросить `architect`. Фактические пробелы импортированного backend перечислены в [backend/docs/README.md](backend/docs/README.md); перенос не означает принятие отсутствующих возможностей.

## 3. Безопасность и данные

Серверные provider credentials не передаются в desktop; клиентская сессия и секреты инкапсулируются вне Renderer. Секреты, `.env`, runtime data, кеши и виртуальные окружения не коммитить. Не логировать диалоги, prompts, ключи или provider internals; не раскрывать их в ошибках API. Конкретные правила Electron/IPC и HTTP boundary — в инструкциях соответствующего каталога.

## 4. Источники и контекст

- Начинать с этого файла, применимой роли (§9) и текущей Issue/запроса. Уже доступные неизменённые источники и результаты не перечитывать; остальные роли и всю документацию по умолчанию не загружать. [Навигатор](docs/README.md) — для поиска источников.
- Искать через `rg --files`/`rg -n`, читать релевантные фрагменты: владение, границы и изменяемые правила контракта; при изменении обмена — обе стороны. При неясности расширять чтение, а не угадывать инварианты.
- Решение architect и Implementation consequences читать в комментариях связанной Issue. Справочные ссылки сами по себе не требуют чтения.

## 5. Зависимости

Сначала использовать существующие зависимости и избегать лишних. До новой внешней npm/Python-зависимости `architect` проверяет: maintenance за последний год; предпочтение pure JS/WASM для desktop и pure Python для backend вместо новой native toolchain; возможность заменить пакет 50–100 строками своего кода. Решение фиксировать в связанной задаче/ADR. npm и Python dependencies остаются отдельными.

В Alpha аудиты безопасности, включая `npm audit` и аналоги, не проводим. Подбор версий Electron, npm/Python-пакетов и lockfile по security advisory — отдельная задача перед финальной выкладкой. Общий запрос QA или запуска не разрешает аудит; advisory, severity и возраст версии не являются основанием для задач обновления или блокировки разработки и приёмки.

Изменение зависимости для реализации назначенной задачи или исправления воспроизводимого дефекта допустимо в её scope с обычными проверками и architect gate, когда он требуется. Правила защиты секретов, изоляции Electron/IPC и валидации данных действуют и в Alpha.

## 6. Код и tooling

Строгие типы, явные имена, без мёртвого кода и неиспользуемых импортов; ориентир — до 300 строк реализации на файл. TypeScript/IPC правила — в desktop-инструкциях; Python и серверная validation — в backend-инструкциях. Tooling/config менять только в явно разрешённом scope задачи.

## 7. Тестирование и рефакторинг

Багфикс начинается с воспроизведения и падающего регрессионного теста. Рефакторинг сохраняет поведение, опирается на тесты и не смешивается с фичами. Unit-тесты мокают внешние адаптеры. Реальные платные/provider вызовы — только в явно разрешённой integration-проверке; не в автоматических тестах.

## 8. Scope и спрайты

- Продуктовые изменения — в `frontend/`, `backend/`, `docs/`, в пределах роли и задачи. Инструкции (`AGENTS.md`, `.agents/**/*.md`) и корневую навигацию меняет `project-manager` в документационной задаче либо исполнитель по прямому поручению пользователя. Править правила ради обхода ограничений запрещено; разрешение на документацию не распространяется на tooling/config.
- Backend использует Python/FastAPI/httpx/Groq и существующие requirements/pytest tooling. Новые стек, подсистема, topology или server storage требуют architect gate. Desktop-документация — в `frontend/docs/`, серверная — в `backend/docs/`, общие материалы и wire-контракты — в `docs/`; исключения: корневые навигаторы и агентские инструкции.
- `frontend/asset-pipeline/` и `discord_orcestrations/` — отдельные внешние скоупы: продуктовым ролям запрещены изменения и запуск их скриптов. Продуктовый diff в них отклоняется. Не откатывать чужие изменения.
- Графику создаёт только внешний художник-человек вне ИИ-системы. Агентам запрещено рисовать, генерировать, нарезать спрайты или ставить такие задачи другим агентам. Размещение готовых ассетов/fallback — по desktop-инструкциям.

## 9. Роли агентов

«Менеджер» означает `project-manager`. Для реализации по умолчанию использовать роль `app-developer`; для вопросов и прямых правок документации роль не требуется. Не присваивать полномочия других ролей.

| Роль | Ответственность |
|---|---|
| [project-manager](.agents/agents/project-manager/agent.md) | Scope, GitHub backlog, маршрутизация, спринты и парные промпты; без продуктового кода. |
| [architect](.agents/agents/architect/agent.md) | Архитектура, инварианты, порты/DTO в коде, Dependency Review; без реализации. |
| [app-developer](.agents/agents/app-developer/agent.md) | Vertical slice во всех слоях: порты/DTO на Fast-Track, desktop/backend реализация и тесты в назначенном scope. |

Fast-Track → `app-developer` по умолчанию. `architect` обязателен по любому из четырёх триггеров:

1. Новая самостоятельная подсистема/технология, новая спецификация движка в `frontend/docs/engine/` или интеграция нового движка (включая persistence или реального AI-провайдера вместо mock). Новый файл или каталог внутри существующей подсистемы сам по себе не является триггером.
2. Сдвиг межслойных/процессных границ, изменение правил изоляции/безопасности или принципиально новые IPC-паттерны.
3. Новая внешняя npm/Python-зависимость.
4. Явный запрос пользователя, `needs:architect`, архитектурный тупик или конфликт контрактов.

Эволюционное расширение портов/DTO в существующих границах — Fast-Track. Разрешение менять каталог не отменяет architect gate.

## 10. Цикл задачи

Исполнитель реализует задачу, устраняет дефекты в её scope и выполняет обязательные проверки. Менеджер подключается после `done`; статусы GitHub Project и закрытие Issues — только менеджер. Одну задачу продолжать в текущем чате, включая изменения desktop и backend. При смене роли или переходе к другой задаче с перегруженным контекстом — новый чат.

Работать в существующей `main`, без новых веток, worktrees и PR. Субагенты используют тот же checkout с согласованным владением файлами. Завершённые задачи сохранять отдельными коммитами и отправлять обычным push в `origin/main`, предварительно проверив актуальность remote. Не переписывать чужую историю и не включать чужие незакоммиченные правки. Другой Git workflow — только по прямому указанию пользователя.

Перед каждым коммитом выполнить из корня `pre-commit run --files <пути файлов коммита>`; для подготовленного индекса без параллельных правок допустим `pre-commit run`. Конфигурация — [`.pre-commit-config.yaml`](.pre-commit-config.yaml). Gate обязателен независимо от установки Git hook и не заменяет проверки §11. Не запускать `--all-files` поверх чужой незавершённой работы без согласованного scope.

После автоисправлений проверить diff, добавить только свои изменения и повторить pre-commit до прохода без изменений; при влиянии на результат повторить gates §11. Ошибка или недоступность pre-commit блокирует коммит; `--no-verify` и `SKIP` запрещены без прямого указания пользователя. `Skipped (no files to check)` допустим для файлов вне конфигурации hooks.

## 11. План, верификация и отчёт

Перед правками определить файлы и короткий план. Делать минимальный законченный vertical slice, использовать существующие абстракции, не менять unrelated files.

| Изменение / роль | Обязательная финальная проверка |
|---|---|
| Desktop реализация / app-developer | `node scripts/wisp.mjs typecheck` и затем `node scripts/wisp.mjs test:frontend` из корня; для интеграции обеих частей — `node scripts/wisp.mjs test` |
| Backend реализация / app-developer | `node scripts/wisp.mjs check:backend`, затем `node scripts/wisp.mjs test:backend` из корня (либо соответствующие Python-команды из `backend/`); при изменении обеих частей также desktop gates |
| Архитектор: порты/DTO в коде | Desktop: `node scripts/wisp.mjs typecheck`; backend: валидация схем без запуска продуктовых тестов; ссылки и лимит спецификаций |
| Docs-only исполнение, включая менеджера | Ссылки, согласованность правил и чистота diff; продуктовые тесты не нужны. Проверяет исполнитель. |

`npm run build` запрещён. Команды маршрутизирует корневой `scripts/wisp.mjs`; npm manifest, lockfile и скрипты находятся в `frontend/`, backend использует requirements/pytest tooling. Новые команды общего tooling — только в явно разрешённой задаче. Сначала запускать затронутые/ранее упавшие тесты, затем gate по таблице; повторять успешные проверки только после влияющих на результат правок. После финального gate scope не расширять.

Для сетевых интеграций проверять недоступность сервера, истечение auth, некорректные ответы, timeout и поздний результат после reset/dispose; повторы записей — при наличии соответствующего use case. Серверные проверки — по [backend/AGENTS.md](backend/AGENTS.md); клиентские gates остаются по таблице.

Для инженерных задач отчёт: `TASK` (ID/scope) → `CHANGES` → `BOUNDARIES` → `SPRITES` (недостающие ключи и требования или `none`) → `VERIFICATION` (результат либо `NOT RUN` с причиной) → `RECOMMENDED NEXT GATE` (`architect`/`blocked`/`done`). Для вопросов и небольших правок документации достаточно краткого ответа с результатом и проверками, если были изменения. Без хронологии и полных логов. При наличии связанной Issue отчёт задачи или решения архитектора публикуется в ней; файлы `*_RESULT.md` запрещены.

## 12. Документация и логи

- Логи: exit code, итог и уникальная диагностика; массовый сбой объяснять общей причиной.
- Спецификации: концепции, инварианты, формулы, FSM-матрицы, компактные таблицы и ссылки на типы. Максимум 450 строк, без минимального объёма. Не копировать типы/псевдокод, общие правила и историю проверок; изменять каноническое правило вместо добавления пересказов.
