# AGENTS: Autonomous Development Team

Этот файл определяет роли, границы ответственности и базовые инженерные правила проекта. Является единым источником технических инвариантов для всех ролей.

## 1. Автономность и платформа

- Project Wisp — **автономное desktop-приложение** (Electron + React + TypeScript).
- **Desktop Offline-First:**
  - Все вычисления и данные хранятся локально на клиенте (SQLite / config files).
  - Серверные прослойки, внешние БД и микросервисы исключены. Исключение — прямой вызов LLM через интерфейс `IAIProvider`.
- **Платформа:**
  - Базовая поддерживаемая платформа — **Linux (Ubuntu / Wayland / X11)**. Целевые — Windows и macOS.
  - Персонаж на экране управляется собственным FSM поведения (`src/domain/character/`) и отображается через Renderer/PixiJS.
- **Кроссплатформенность:**
  - Пути: только `path.join`, никаких ручных слэшей в файловых операциях.
  - Регистр: в коде и документации имена файлов и импорты должны строго совпадать с регистром на файловой системе (чувствительность Linux).
  - Любая специфика ОС и платформенные ветвления (`process.platform`) изолируются исключительно в адаптерах: `src/infrastructure/platform/` за общими портами (`IPlatformAdapter`).

## 2. Архитектура и изоляция слоёв (Clean Architecture)

- **Domain:**
  - Содержит чистую бизнес-логику, математику, FSM поведения, состояние персонажа (Needs, Mood), кинематику и правила анимации.
  - Полная изоляция: чистый детерминированный TypeScript без зависимостей от React, Electron, Node.js (`fs`, `path`, `os`), SQLite, UI или AI SDK. Время, RNG и внешние события передаются явными параметрами.
- **Application:**
  - Содержит use cases, команды, запросы и объявляет интерфейсы портов (`src/application/ports/`). Порт определяется потребителем (Application), адаптер реализуется в Infrastructure.
  - Слой остаётся платформенно-нейтральным и не зависит от UI.
- **Infrastructure:**
  - Реализует порты (`src/infrastructure/`), инкапсулирует вызовы Electron, ОС, файловой системы, SQLite и AI-провайдеров.
- **Main Process:**
  - Владеет жизненным циклом окон, IPC-обработчиками, оркестрацией use cases и DI-композицией. Только Main выполняет внешние сетевые вызовы (AI-провайдеры).
- **Contracts-First & Architecture-as-Code:**
  - Объявление типизированных интерфейсов портов в `src/application/ports/` и DTO в `src/shared/ipc-contracts.ts` обязательно выполняется **до начала** разработки адаптеров и сервисов реализации.
- **Разделение подсистем и движков:**
  - `IAIProvider` возвращает семантический DTO и не имеет доступа к React, DOM, стилям или кадрам анимации.
  - Render Engine отвечает за visual props, слои, границы и масштабирование (`docs/engine/RENDER_ENGINE.md`).
  - Animation Engine управляет клипами, приоритетами и прерываниями (`docs/engine/ANIMATION_ENGINE.md`).
- **Спецификации движков (`docs/engine/*.md`):**
  - Целевой объём файла спецификации — 250–400 строк (жёсткий лимит — 450 строк).
  - Фиксируются только концепции, инварианты, формулы, матрицы переходов FSM и компактные таблицы со ссылками на типы в кодовой базе (`src/application/ports/`, `src/shared/ipc-contracts.ts`), без раздувания простыней псевдокода.

## 3. Безопасность Electron и изоляция IPC

- **Настройки BrowserWindow:** `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true` — обязательны для всех окон.
- **IPC через Preload:**
  - Renderer общается с Main исключительно через типизированный мост `window.wispAPI` (`src/preload/`). Прямой вызов `ipcRenderer.send/invoke` со строковыми каналами исключён.
  - Все входные данные IPC валидируются в Main-процессе перед обработкой.
- **Сетевая безопасность:** Renderer не выполняет сетевых запросов. Доступ в сеть изолирован в Main.

## 4. UI и Renderer слой

- **Тупой UI (Dumb UI):** React-компоненты отвечают только за отображение текущего презентационного состояния (`presentation state`) и трансляцию действий пользователя в IPC. Никакой бизнес-логики, физики или FSM в React.
- **Производительность:**
  - Избегать лишних ререндеров визуальных компонентов.
  - Анимации используют `requestAnimationFrame` или CSS transforms (`transform: translate3d(...)`).
  - Изменение позиции окна — через IPC-батчинг, а не попиксельные частые синхронные вызовы.

## 5. Зависимости (Zero New Dependencies First)

- Любая внешняя библиотека требует архитектурного обоснования (YAGNI). Предпочтение собственным минималистичным решениям на TypeScript перед добавлением библиотек.
- Новую npm-зависимость до реализации оценивает `architect`:
  1. Лицензия: пермиссивная (MIT, Apache 2.0, BSD, ISC).
  2. Размер и transitives: минимальный bundlephobia / overhead.
  3. Активность: активный maintenance за последний год, отсутствие открытых критических CVE.
  4. Нативные биндинги: предпочтение pure JS/WASM перед native C++ (node-gyp риски сборки).
  5. Альтернатива: возможность написать 50–100 строк собственного кода вместо добавления пакета.

## 6. Качество кода и TypeScript

- **Строгая типизация (Strict Mode):**
  - Никаких `any` (использовать `unknown` с type guards).
  - Никаких `as unknown as Type` (двойных приведений) и подавления ошибок через `@ts-ignore` (`@ts-expect-error` допустим только с обязательным комментарием причины).
  - Строгие типы для всех IPC-сообщений, событий и доменных сущностей (`readonly` свойства по умолчанию).
- **Code Style & Чистота:**
  - Имена функций и переменных явно отражают намерение.
  - Никаких неиспользуемых импортов, переменных и мёртвого кода.
  - Файлы организованы логично: целевой размер до 300 строк на файл реализации.

## 7. Тестирование, TDD и рефакторинг

- **TDD для багфиксов:** воспроизведение бага и написание падающего регрессионного теста до внесения исправлений.
- **Рефакторинг:** сохраняет поведение, проводится при наличии тестов и не смешивается с добавлением новой функциональности.
- **Изоляция unit-тестов:** моки для внешних адаптеров, никаких реальных таймеров без vitest fake timers.

## 8. Продуктовый скоуп, внешние скоупы и графика

- **Продуктовый скоуп приложения:** разработка ведётся исключительно в продуктовых папках (`src/`, `public/`, `tests/`, `docs/`).
- **Изолированные внешние скоупы (`asset-pipeline/` и `discord_orcestrations/`):**
  - Полностью автономные области. Всем продуктовым ролям (`architect`, `app-developer`, `reviewer`, `project-manager`) категорически запрещено модифицировать файлы, конфиги и скрипты внутри этих папок.
  - Запрещён запуск скриптов нарезки/генерации (`python3 asset-pipeline/...`) и скриптов Discord-бота. Любой diff в этих папках подлежит немедленному отклонению на review.
- **Правило графики и спрайтов:** готовые спрайты и анимации берутся исключительно из `public/assets/sprites/` (манифест: `public/assets/sprites/manifest.json`).
  - Графику создаёт исключительно **внешний художник-человек вне ИИ-системы** и помещает в `public/assets/sprites/`. Задачи по рисованию или генерации графики на ИИ-агентов категорически не заводятся.
  - Разработчик (`app-developer`) спрайты самостоятельно **НЕ создаёт, не генерирует, не нарезает и не рисует**, и **не меняет файлы внутри `asset-pipeline/`**.
  - При отсутствии нужных файлов в коде обязательно применяется временный fallback/заглушка/алиас, а разработчик **обязан зафиксировать запрос для художника-человека в реестре [docs/art/SPRITE_REQUESTS.md](docs/art/SPRITE_REQUESTS.md)** и указать список в строке `SPRITES:` своего отчёта.

Общий навигатор — [docs/README.md](docs/README.md). `ARCHITECTURE.md` — обзор для людей, не входит в обязательный контекст агента.

## 9. Роли агентов

Перед работой прочитать инструкцию назначенной роли по ссылке ниже, не остальные роли. «Ты менеджер» или «менеджер проекта» означает `project-manager`.

- [project-manager](.agents/agents/project-manager/agent.md): scope, маршрутизация задач (Fast-Track по умолчанию, Architect только по 4 триггерам), task backlog в GitHub Issues. Не меняет продуктовый код. Предоставляет парные промты с рекомендацией по контексту. Подключается после завершения задачи (`Approved` / `done`).
- [architect](.agents/agents/architect/agent.md): архитектура подсистем, инварианты в `docs/engine/*` и объявление целевых контрактов в кодовой базе (типы портов в `src/application/ports/` и DTO в `src/shared/ipc-contracts.ts`). Актуализирует интерфейсы в коде. Dependency Review.
- [app-developer](.agents/agents/app-developer/agent.md): реализация задач на Fast-Track (объявление/расширение портов и DTO, Domain/Application, Main/Preload, Renderer, adapters, packaging), реализация логики, сервисов, UI и тестов. Не генерирует спрайты сам (графику рисует художник-человек; разработчик фиксирует запросы в `docs/art/SPRITE_REQUESTS.md`).
- [reviewer](.agents/agents/reviewer/agent.md): review, verification, audit diff. Проверяет контракты архитектора и реализацию разработчика (`npm run typecheck`). Блокирует любые изменения вне продуктового скоупа. Имеет право на точечный Fast-Fix мелких неточностей типов/тестов без возврата задачи. Lean Verification: запускает только быстрый `npm run typecheck` (~1 сек) и проводит аудит diff; запуск `npm test` ревьюером исключён (включая Fast-Fix).

## 10. Автономный цикл реализации

Роли (`architect`, `app-developer`, `reviewer`) работают внутри цикла задачи (`implementation/fixes <-> review`) автономно без передачи промежуточных шагов менеджеру. Project Manager подключается только после закрытия задачи (`Approved` / `done`).

- **Непрерывность контекста (Same-Scope Continuity):**
  - При выполнении цепочки задач в рамках одного трека/подсистемы (например, Phase 14 / `track:shimeji`) под одной ролью (`app-developer`) рекомендуется продолжать работу в текущем чате для переиспользования прогретого контекста кодовой базы.
  - Запуск нового чата рекомендуется при смене роли (`architect` $\to$ `app-developer`), кардинальной смене подсистемы или переполнении контекста длинными отладочными логами.

## 11. Рабочие правила и верификация

Перед правками определить затронутые файлы и короткий план. Делать самый маленький vertical slice, который закрывает задачу. Использовать существующие абстракции. Сохранять кроссплатформенные границы. Не менять unrelated files и не откатывать чужие изменения.

**Lean Verification по ролям:**
- **Задачи реализации (`owner: app-developer`):** разработчик обязан запустить `npm run typecheck && npm test` перед сдачей в review.
- **Архитектурные задачи с контрактами (`owner: architect`):** архитектор обязан запустить `npm run typecheck` (гарантия компилируемости добавленных/изменённых портов и DTO в `src/`), проверить ссылки markdown и лимит строк (<= 450 строк). Продуктовые тесты пишутся разработчиком при реализации.
- **Независимое ревью (`owner: reviewer`):** ревьюер запускает только быстрый `npm run typecheck` (~1 сек) и проводит аудит diff; запуск `npm test` ревьюером полностью исключён.
- **Docs-only изменения (README, руководства):** проверяются корректность ссылок и чистота diff, запуск тестов не требуется.
- **Build:** `npm run build` не запускать ни при каких задачах — проект ещё не находится на стадии build-верификации. Использовать только существующие в `package.json` скрипты (не выдумывать несуществующие lint gates).
- **Project Manager:** не запускает продуктовые тесты для обычной работы с документацией и планированием.

**Общий отчёт исполнителя:** `TASK` (Task ID, scope) → `CHANGES` → `BOUNDARIES` → `SPRITES` (зафиксированные в `docs/art/SPRITE_REQUESTS.md` или `none`) → `VERIFICATION` (результаты или `NOT RUN` с причиной) → `RECOMMENDED NEXT GATE` (`reviewer` / `architect` / `blocked` / `done`).

## 12. Экономия контекста и проверок

- Использовать минимально необходимый контекст: сначала искать имена файлов и точные совпадения (`rg`, `rg --files`), затем читать только релевантные фрагменты.
- Не перечитывать неизменённые файлы и уже полученные результаты, пока они надёжно присутствуют в текущем контексте.
- Не исследовать соседние подсистемы без конкретной связи с задачей.
- При разработке и исправлениях сначала запускать затронутые тесты и ранее упавшие проверки.
- Финальную верификацию выполнять строго по правилам роли из раздела 11. Не запускать `npm test` для ролей и типов задач, которым это запрещено.
- Успешную проверку повторять только после изменений, способных повлиять на её результат.
- `npm run build` не запускать ни при каких обстоятельствах.
- Объёмные логи при необходимости сохранять во временный файл вне продуктового diff. В контекст возвращать только exit code, итог проверки и уникальные диагностические сообщения.
- При массовом однотипном сбое сначала определить и описать общую первопричину. Не возвращать повторяющуюся ошибку для каждого файла.
- После успешной обязательной верификации не расширять scope и не добавлять проверки без конкретного технического основания.
- Итоговый отчёт оформлять по установленному шаблону: `TASK` → `CHANGES` → `BOUNDARIES` → `SPRITES` → `VERIFICATION` → `RECOMMENDED NEXT GATE`, без хронологического пересказа работы.
