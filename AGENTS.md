# AGENTS: Project Wisp

Общие инженерные инварианты монорепозитория. Инструкции ролей и каталогов дополняют этот файл, не дублируют и не ослабляют его. Desktop-специфика — в [frontend/AGENTS.md](frontend/AGENTS.md), серверная — в [backend/AGENTS.md](backend/AGENTS.md). При изменении desktop tooling в корне читать desktop-правила; при изменении общей документации — правила затронутых частей.

## 1. Автономность и платформа

Desktop и backend — самостоятельные приложения с отдельными runtime, зависимостями, тестами и запуском. Desktop находится в `frontend/` (`frontend/src/`, `frontend/public/`, `frontend/tests/`); Python/FastAPI backend находится только в `backend/`.

Offline-first относится к локальному runtime персонажа и локальным данным desktop (SQLite/config files). Сетевые функции могут требовать подключения; недоступность backend не останавливает локальные FSM, Motion и ввод. Windows — первая платформа приёмки desktop; Linux и macOS сохраняются с capability fallback.

## 2. Архитектура и контракты

- Backend — отдельная граница исполнения, со своими API, внешними интеграциями и серверным хранением. Клиентские use cases используют Application ports; транспорт и auth инкапсулируют Infrastructure adapters, создаваемые Main. Backend не управляет напрямую локальными FSM, физикой или Renderer. Для AI допустимы backend-backed `IAIProvider` и прямой LLM-вызов.
- До реализации сетевой функции определить обе стороны API, валидацию, совместимость версий, ошибки, auth, deadline/cancellation, retry/idempotency и поведение при потере связи. Серверный wire contract отделён от локальных Application ports и IPC DTO; ответ валидируется и преобразуется адаптером до использования Application.
- До передачи или серверного хранения данных определить разрешённый состав, владельца/source of truth, сроки хранения и удаление. Для sync задать разрешение конфликтов и восстановление после разрыва связи. Локальная очистка не означает удаление серверной копии.
- Канонические desktop engine-спецификации — в [frontend/docs/engine/](frontend/docs/engine/README.md), общие API-контракты — в [docs/contracts/](docs/contracts/README.md), wire fixtures — в `docs/contracts/fixtures/`. Python-схемы и TypeScript-типы не импортируют друг друга; fixtures проверяют совместимость.
- При конфликте спецификации и реализации не выбирать удобную версию: остановить затронутую часть и запросить `architect`. Фактические пробелы импортированного backend перечислены в [backend/docs/README.md](backend/docs/README.md); перенос не означает принятие отсутствующих возможностей.

## 3. Безопасность и данные

Серверные provider credentials не передаются в desktop; клиентская сессия и секреты инкапсулируются вне Renderer. Секреты, `.env`, runtime data, кеши и виртуальные окружения не коммитить. Не логировать диалоги, prompts, ключи или provider internals; не раскрывать их в ошибках API. Конкретные правила Electron/IPC и HTTP boundary — в инструкциях соответствующего каталога.

## 4. Владение реализацией

Desktop владеет локальными FSM, Needs/Mood, физикой, анимациями, presentation и пользовательским вводом. Backend владеет серверными внешними интеграциями и формированием AI-ответа, возвращает только разрешённые семантические DTO. Один репозиторий не разрешает прямые импорты между границами исполнения или перенос бизнес-решений в Renderer.

## 5. Зависимости

Zero New Dependencies First / YAGNI. До новой внешней npm/Python-зависимости `architect` проверяет: пермиссивную лицензию (MIT/Apache-2.0/BSD/ISC); размер и transitives; maintenance за последний год и отсутствие открытых critical CVE; предпочтение pure JS/WASM для desktop и pure Python для backend вместо новой native toolchain; возможность заменить пакет 50–100 строками своего кода. Пятифакторное решение фиксировать в связанной задаче/ADR. npm и Python dependencies остаются отдельными.

## 6. Код и tooling

Строгие типы, явные имена, без мёртвого кода и неиспользуемых импортов; ориентир — до 300 строк реализации на файл. TypeScript/IPC правила — в desktop-инструкциях; Python и серверная validation — в backend-инструкциях. Tooling/config менять только в явно разрешённом scope задачи.

## 7. Тестирование и рефакторинг

Багфикс начинается с воспроизведения и падающего регрессионного теста. Рефакторинг сохраняет поведение, опирается на тесты и не смешивается с фичами. Unit-тесты мокают внешние адаптеры. Реальные платные/provider вызовы — только в явно разрешённой integration-проверке; не в автоматических тестах.

## 8. Scope и спрайты

- Продуктовые изменения — в `frontend/`, `backend/`, `docs/`, в пределах полномочий назначенной роли. Инструкции (`AGENTS.md`, вложенные `AGENTS.md`, `.agents/**/*.md`) и корневую навигацию меняет `project-manager` в своей документационной задаче либо исполнитель по прямому поручению пользователя изменить эти документы. Разработчик, архитектор и ревьюер не правят правила ради обхода ограничений своей задачи; tooling/config этим исключением не разрешены.
- Backend-код — только `backend/`, стек Python/FastAPI/httpx/Groq и существующие requirements/pytest tooling. Новые стек, подсистема, topology или server storage требуют architect gate. Desktop-документация — в `frontend/docs/`, серверная — в `backend/docs/`, общие материалы и wire-контракты — в `docs/`; исключения: корневые навигаторы и агентские инструкции.
- `frontend/asset-pipeline/` и `discord_orcestrations/` — отдельные внешние скоупы: продуктовым ролям запрещены изменения и запуск их скриптов. Продуктовый diff в них отклоняется. Не откатывать чужие изменения.
- За исключением явно назначенной пользователем роли `rigger` в скоупе ниже, графику создаёт только внешний художник-человек вне ИИ-системы. Остальным агентам запрещено рисовать, генерировать, нарезать спрайты или ставить такие задачи другим агентам. Размещение готовых ассетов/fallback — по desktop-инструкциям.

### Исключение: агент-риггер (`rigger`)

По прямому поручению пользователя агент-риггер самостоятельно готовит персонажа в `rig_animations/`, а пользователь проверяет результаты этапов. В этом скоупе разрешены выделение исходных пикселей масками, разделение изображения на слои, создание и редактирование технических сеток, перекрытий, деформеров, параметров и анимаций, сохранение, повторное открытие и экспорт модели. Работа через установленный PSD2Live и его MCP разрешена; требование внешнего художника на этот процесс не распространяется. Разделение исходных пикселей и создание технической сетки не требуют повторного разрешения по общему запрету выше.

Риггер использует [skill wisp-psd2live](rig_animations/skills/wisp-psd2live/SKILL.md) и [поэтапный процесс приёмки](rig_animations/README.md): один участок и один этап за итерацию, затем просмотр пользователем. Перед подготовкой нового движения пользователь принимает целевую картинку конечной позы; для цикла с одинаковыми началом и концом — наиболее выраженную позу внутри цикла. В пределах порученного этапа агент выполняет техническую работу сам; переходы между этапами требуют явного принятия либо прямого расширения скоупа пользователем. Браузерные схемы и целевые картинки служат для обсуждения и сравнения, а реальные слои и риг редактируются в рабочем проекте редактора.

Исходное изображение и прежние прототипы сохраняются; новые варианты создаются в отдельных рабочих копиях. Риггер может редактировать исходную картинку для получения целевой позы и восстанавливать скрытую кожу, ткань и другие недостающие поверхности только после согласования конкретной области/маски, метода, локального или облачного выполнения, передач данных и затрат; результат также проходит приёмку. Принятие целевой картинки задаёт образец внешнего вида, но не принимает риг и не разрешает автоматически перенос сгенерированных пикселей в его слои. Разрешение на разделение слоёв само по себе не разрешает дорисовку. Исключение не даёт права менять продуктовый runtime, зависимости или `frontend/asset-pipeline/` и не отменяет остальных инженерных границ.

По прямому поручению пользователя разрешён также отдельный слой PNG по референсу: сначала получить полную форму детали, включая необходимый скрытый запас, проверить её отдельно и в нейтральной сборке, затем использовать выбранный слой в рабочей копии рига. Подробный процесс — в [README](rig_animations/README.md#отдельный-слой-по-референсу). При проверке одного движения соседние детали остаются неподвижными, если их изменение не включено в задачу. Для текущего взгляда двигаются только радужки со зрачками и бликами; веки, белки и форма глаз не изменяются. Приёмка нового слоя не принимает автоматически контроллер или анимацию.


## 9. Роли агентов

Читать только назначенную роль. «Менеджер» означает `project-manager`. Если роль не назначена, выполнять запрос пользователя в его scope, не загружая инструкции всех ролей. Отсутствие роли не отменяет общие границы и проверки; агент не присваивает себе полномочия остальных ролей.

| Роль | Ответственность |
|---|---|
| [project-manager](.agents/agents/project-manager/agent.md) | Scope, GitHub backlog, маршрутизация, спринты и парные промпты; без продуктового кода. |
| [architect](.agents/agents/architect/agent.md) | Архитектура, инварианты, порты/DTO в коде, Dependency Review; без реализации. |
| [app-developer](.agents/agents/app-developer/agent.md) | Vertical slice во всех слоях: порты/DTO на Fast-Track, desktop/backend реализация и тесты в назначенном scope. |
| `rigger` | Подготовка слоёв, риг и анимации в `rig_animations/` через PSD2Live/MCP, по исключению раздела 8 и с поэтапной приёмкой пользователем; без продуктовой интеграции. |

Fast-Track → `app-developer` по умолчанию. `architect` обязателен по любому из четырёх триггеров:

1. Новая подсистема/технология: новый модуль в `frontend/src/domain/`, новая спецификация движка в `frontend/docs/engine/`, интеграция нового движка (включая persistence или реального AI-провайдера вместо mock).
2. Сдвиг межслойных/процессных границ, изменение правил изоляции/безопасности или принципиально новые IPC-паттерны.
3. Новая внешняя npm/Python-зависимость.
4. Явный запрос пользователя, `needs:architect`, архитектурный тупик или конфликт контрактов.

Эволюционное расширение портов/DTO в существующих границах — Fast-Track. Наличие этих каталогов в разрешённом scope не позволяет обходить architect gate.

## 10. Цикл задачи

Исполнитель реализует задачу, устраняет обнаруженные дефекты и выполняет обязательные проверки. Менеджер подключается после `done`. Статусы GitHub Project и закрытие Issues — только менеджер. Одна роль и подсистема — продолжать текущий чат; смена роли/подсистемы или перегруженный контекст — новый чат.

В текущей итерации работа ведётся только в существующей ветке `main`: новые Git-ветки, worktrees и PR для задач не создавать. Субагенты работают в том же checkout с согласованным владением файлами. Завершённые изменения сохранять отдельными task-scoped коммитами в `main` и отправлять в `origin/main` обычным push; перед push проверить актуальность remote, не переписывать чужую историю и не включать чужие незакоммиченные правки. Другой Git workflow допускается только по новому прямому указанию пользователя.

## 11. План, верификация и отчёт

Перед правками определить файлы и короткий план. Делать минимальный законченный vertical slice, использовать существующие абстракции, не менять unrelated files.

| Изменение / роль | Обязательная финальная проверка |
|---|---|
| Desktop реализация / app-developer | `node scripts/wisp.mjs typecheck` и затем `node scripts/wisp.mjs test:frontend` из корня; для интеграции обеих частей — `node scripts/wisp.mjs test` |
| Backend реализация / app-developer | `node scripts/wisp.mjs check:backend`, затем `node scripts/wisp.mjs test:backend` из корня (либо соответствующие Python-команды из `backend/`); при изменении обеих частей также desktop gates |
| Архитектор: порты/DTO в коде | Desktop: `node scripts/wisp.mjs typecheck`; backend: валидация схем без запуска продуктовых тестов; ссылки и лимит спецификаций |
| Docs-only исполнение, включая менеджера | Ссылки, согласованность правил и чистота diff; продуктовые тесты не нужны. Проверяет исполнитель. |
| Риг / rigger | Проверки текущего этапа по skill: сохранность исходника, визуальная проверка слоёв/поз; при изменении проекта — сохранение и повторное открытие, при экспорте — проверка результата. Продуктовые тесты для изолированного авторинга не нужны. |

`npm run build` запрещён для всех задач. Корневой Node CLI `scripts/wisp.mjs` маршрутизирует команды; package.json и lockfile находятся только в `frontend/`; desktop скрипты и зависимости — в `frontend/package.json`, backend — существующие requirements/pytest tooling. Новые команды общего tooling допустимы только в явно разрешённой задаче. Сначала затронутые/ранее упавшие тесты; финальный gate по таблице. Успешные проверки повторять только после влияющих на результат изменений. После обязательной проверки scope не расширять.

Для сетевых интеграций проверять недоступность сервера, истечение auth, некорректные ответы, timeout и поздний результат после reset/dispose; повторы записей — при наличии соответствующего use case. Серверные проверки — по [backend/AGENTS.md](backend/AGENTS.md); клиентские gates остаются по таблице.

Отчёт: `TASK` (ID/scope) → `CHANGES` → `BOUNDARIES` → `SPRITES` (недостающие ключи и требования из задачи или `none`) → `VERIFICATION` (результат либо `NOT RUN` с причиной) → `RECOMMENDED NEXT GATE` (`architect`/`blocked`/`done`). Без хронологии и полных логов. Отчёты задач и решений архитекторов в текущей итерации публикуются в соответствующей Issue; создание файлов `*_RESULT.md` в репозитории запрещено.

## 12. Экономия контекста и документация

- Стартовый контекст: этот файл (если уже передан — не перечитывать), назначенная роль, текущая Issue/запрос. [Навигатор](docs/README.md) нужен только для поиска источника.
- Сначала `rg --files`/`rg -n`, затем релевантные фрагменты. Для затронутого контракта читать владение/границы и изменяемые правила; при изменении обмена — обе стороны. Расширять чтение при неясности, не угадывать инварианты ради экономии.
- Не загружать всё `docs/`, чужие роли, историю отчётов или `ARCHITECTURE.md` по умолчанию. Связанный architect result и его Implementation consequences берутся из комментариев к связанной Issue; справочные ссылки не являются командой прочитать всё.

- Не перечитывать неизменённые источники/результаты, уже доступные в контексте. Логи возвращать как exit code, итог и уникальную диагностику; массовый сбой объяснять общей причиной.
- Спецификации: концепции, инварианты, формулы, FSM-матрицы, компактные таблицы и ссылки на типы. Максимум 450 строк, **без минимального объёма**; не раздувать до 250–400 строк. Не копировать типы/псевдокод, общие правила или историю проверок. Изменять каноническое правило вместо дописывания его очередного пересказа.
